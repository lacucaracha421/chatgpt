# Lakomics 제품 변경 백로그

> 상태: 요구사항 수집 중
> 시작일: 2026-08-24
> 목적: 사용자 제안을 그대로 확정하지 않고 현재 구현, 제품 원칙, 데이터 위험을 대조해 기록한다.

## 판단 표기

- **수용**: 방향이 타당하고 기존 제품 결정과도 일치한다.
- **수정 수용**: 문제는 타당하지만 제안한 해결책은 범위나 접근 방식을 다듬어야 한다.
- **보류**: 식별 기준이나 성공 조건이 부족해 구현 결정을 내릴 수 없다.

## 1. 온라인 망가 카탈로그의 갱신 경로 정비

### 사용자 관찰

망가 카탈로그 데이터를 업데이트하는 방법이 보이지 않는다. 다른 프로젝트의 로컬 데이터를 가져와 일회성으로 사용하는 것처럼 보인다.

### 현재 구현 확인

- 최초 설치 시 사용자가 선택한 VCK 폴더의 `kdata.db`, 검색 제안, 태그 번역을 Lakomics 라이브러리의 `catalogs` 아래로 복사하고 검증한다.
- 설치 후 온라인 카탈로그 화면에는 `지금 갱신` 명령이 있다. Lakomics는 숨겨진 WebView에서 `https://k-hentai.org/ajax/search?search=language:korean`를 호출해 데이터를 직접 가져온다.
- 설정에는 자동 갱신과 1시간, 6시간, 24시간 간격 선택이 있다.
- 앱은 시작 시와 실행 중 매시간 갱신 필요 여부를 확인한다.
- 갱신은 로컬 최대 작품 ID보다 큰 신규 작품만 추가한다. 한 번에 최대 40페이지, 페이지당 50개를 처리한다.
- 기존 작품의 제목·태그·상태 변경이나 원격 삭제는 반영하지 않는다. 태그 한국어 번역 파일도 최초 VCK 가져오기 이후 자동 갱신하지 않는다.
- 설치가 끝난 뒤 VCK 원본 폴더를 다시 선택하여 전체 카탈로그를 교체하거나 복구하는 경로는 화면에 노출되지 않는다.

### 비판적 판단 — 수정 수용

“업데이트 기능이 없다”는 진단 자체는 정확하지 않다. Lakomics가 k-hentai에서 직접 신규 작품을 가져오는 수동·자동 증분 갱신은 이미 존재한다. 그러나 이는 기존 레코드까지 맞추는 완전 동기화가 아니라 append-only 신규 수집이다. 최초 가져오기와 이후 온라인 갱신이 서로 다른 위치에 있고, 설치 상태·마지막 성공·오류·추가된 작품 수가 충분히 드러나지 않아 사용자가 갱신 구조를 발견하거나 신뢰하기 어렵다. 또한 설치 후 전체 교체/복구 경로가 없어 최초 가져오기는 실제로 일회성 부트스트랩에 가깝다.

### 권장 방향

카탈로그 관리 동작을 다음 세 가지로 명확히 분리한다.

1. **초기 설치**: VCK 로컬 데이터로 카탈로그를 최초 구성한다.
2. **신규 작품 갱신**: k-hentai에서 로컬 최대 ID 이후의 새 작품을 증분 반영하며 수동 실행과 자동 주기를 제공한다.
3. **교체/복구**: 사용자가 VCK 폴더를 다시 선택해 전체 카탈로그를 검증 후 교체한다.

현재 기능을 과장하지 않도록 UI에서도 `신규 작품 확인`처럼 범위를 드러내는 이름을 검토한다. 일반 화면에는 자주 쓰는 명령과 마지막 갱신 상태만 두고, 원본 재선택·전체 교체는 설정의 카탈로그 관리 영역에 둔다. 전체 교체는 북마크와 읽기 기록 같은 Lakomics 소유 데이터를 보존해야 한다. 기존 작품 변경까지 반영하는 진짜 동기화는 별도 요구사항으로 취급한다.

### 완료 기준 초안

- 사용자가 현재 카탈로그의 설치 여부, 작품 수, 마지막 성공 시각과 최근 오류를 확인할 수 있다.
- 사용자가 화면에서 즉시 수동 갱신을 실행할 수 있다.
- 자동 갱신의 활성 여부와 주기를 이해하고 변경할 수 있다.
- UI가 신규 작품 추가와 기존 작품 동기화를 혼동시키지 않는다.
- 설치 후에도 전체 카탈로그 교체/복구가 가능하며 실패 시 기존 카탈로그가 보존된다.

### Project Violet 참고 조사

2026-08-24 기준 `project-violet/violet`의 `fdb561c` 소스를 확인했다. 최신 Violet에는 서로 다른 두 갱신 방식이 공존한다.

#### `fast-hsync` 직접 수집기

- Hitomi의 gallery block과 gallery JS를 직접 받아 `HitomiColumnModel` SQLite 테이블을 갱신한다.
- 기본 실행은 현재 최대 ID 앞뒤 약 1만 개씩을 조사한다.
- 기본값은 기존 ID를 건너뛰지만 `--force` 실행은 기존 항목도 다시 받아 변경 여부를 비교한다.
- 새 항목과 변경 항목을 `INSERT OR REPLACE`하고 관련 FTS row도 갱신한다.
- 변경분을 `chunk/data-*.json`으로 내보낼 수 있다.
- 선택적으로 ExHentai 메타데이터를 합칠 수 있으나 사용자 쿠키가 필요하다.
- 구현의 기본 동시 요청 수가 1,024라서 일반 데스크톱 앱에 그대로 적용하기에는 공격적이다.

#### Violet Web 배포 DB/청크 소비자

- 공개 인덱스에서 전체 DB와 변경 JSON 청크 목록을 읽는 구조다.
- 로컬 DB가 없거나 마지막 전체 DB 교체 후 7일이 지났거나 누적 청크가 10MB를 넘으면 전체 DB를 다시 받는다.
- 그 외에는 체크포인트보다 새 청크만 오래된 순서로 적용한다.
- 수동 일반 동기화, 강제 전체 동기화, 진행 상태 API를 분리한다.
- 코드가 참조하는 `https://raw.githubusercontent.com/violet-dev/sync-data/master/syncversion.txt`는 조사 시점에 404를 반환했다. 현재 공개 배포 인프라로 바로 의존할 수 있다고 가정하면 안 된다.

#### Lakomics에 그대로 적용할 수 없는 이유

- 최신 Violet은 `HitomiColumnModel` 스키마를 사용하지만 현재 Lakomics의 VCK 가져오기는 `Works/Tags/CrawlState` 스키마를 요구한다.
- Violet 저장소 루트에서 명시적 라이선스 파일을 확인하지 못했다. 코드를 복사하지 않고 동작 원리만 참고한다.
- 외부 프로젝트가 운영하는 비공개 또는 불안정한 배포 인덱스에 Lakomics의 핵심 기능을 결합하면 다시 단일 장애점이 생긴다.
- Violet Web의 전체 DB 교체 경로는 다운로드 완료 후 임시 파일을 쓰지만, Lakomics가 요구하는 명시적 스키마·무결성 검증과 사용자 데이터 보존 절차를 별도로 설계해야 한다.

#### 수정된 권장 방향

1. **단기 권장**: Lakomics 내부 갱신기를 유지하되 최신 ID 주변의 제한된 재검사 구간을 두어 신규 항목뿐 아니라 변경된 기존 항목도 비교·upsert한다. 요청 동시성, 재시도, 속도 제한은 보수적으로 유지한다.
2. **복구 경로**: VCK 또는 호환 가능한 전체 카탈로그를 다시 선택해 검증 후 원자적으로 교체할 수 있게 한다.
3. **장기 후보**: 신뢰할 수 있는 배포 주체와 안정적인 manifest URL이 확보될 때만 전체 스냅샷+서명/체크섬+변경 청크 방식을 도입한다.
4. **비권장**: 현재 404인 Violet 배포 인덱스에 직접 의존하거나 Violet의 Go/TypeScript 코드를 그대로 복사한다.

### Pupil 참고 조사

2026-08-24 기준 `pupil/Pupil`의 `59454c1` 소스를 확인했다. Pupil은 Android용 Hitomi.la 뷰어이며, 전체 카탈로그 SQLite를 설치하거나 갱신하지 않는다.

#### 검색과 목록 구성 방식

- 앱 시작 이후 Hitomi의 `tagindex/version`과 `galleriesindex/version`을 읽어 현재 원격 인덱스 버전을 사용한다.
- 기본·태그·언어·인기 정렬 목록은 원격 `.nozomi` 파일에서 gallery ID 집합을 읽는다.
- 일반 문자열 검색은 원격 B-tree index 일부를 HTTP Range 요청으로 읽고, 해당 data 구간에서 gallery ID를 얻는다.
- 검색 제안은 `tagindex.hitomi.la`의 경로 기반 JSON 응답을 직접 사용한다.
- 검색 결과 단계에서는 ID만 다루고, 화면에 필요한 작품은 `galleries/{id}.js`를 지연 조회해 제목, 작가, 시리즈, 태그, 이미지 목록을 구성한다.
- 조회한 gallery metadata와 이미지 파일은 작품별 캐시에 저장하지만 전체 검색 인덱스는 로컬에 보관하지 않는다.

#### 장점

- 초기 VCK 데이터나 전체 카탈로그 설치가 필요 없다.
- 별도의 카탈로그 갱신 버튼 없이 원격 Hitomi 인덱스의 최신 상태를 사용한다.
- 필요한 index byte range와 현재 보는 작품 상세만 받아 로컬 저장 공간을 절약한다.
- 즐겨찾기, 검색 기록, 다운로드는 원격 카탈로그와 분리해 로컬에 보존한다.

#### 한계

- 네트워크가 없으면 전체 카탈로그 검색과 새 작품 탐색이 불가능하다.
- Hitomi의 비공식 index 파일 형식, 도메인, URL 계산 규칙 변화에 직접 영향을 받는다.
- 전체 카탈로그를 로컬 SQL로 자유롭게 분석하거나 오프라인 검색하기 어렵다.
- 원격 검색이 실패할 때 사용할 완전한 로컬 fallback이 없다.
- 개별 소스 파일에는 Apache-2.0 고지가 있지만 앱 Module에는 GPL-3.0 라이선스가 있어 코드 복사 전 라이선스 범위를 별도로 검토해야 한다. 설계 원리만 참고하는 편이 안전하다.

#### Lakomics에 주는 선택지

1. **원격 검색형**: Pupil처럼 Hitomi 원격 인덱스를 직접 검색하고 열어 본 작품만 캐시한다. 항상 최신인 대신 오프라인 전체 검색을 포기한다.
2. **로컬 카탈로그형**: Violet처럼 전체 DB 또는 자체 수집 DB를 유지한다. 오프라인 검색이 가능하지만 설치·갱신·복구 비용이 남는다.
3. **혼합형**: 원격 검색을 기본으로 삼고 북마크·열람 작품 metadata는 로컬 캐시하며, 전체 로컬 카탈로그는 선택 기능으로 둔다. 기능 범위가 커지므로 실제 오프라인 전체 검색 요구가 있을 때만 채택한다.

#### 현재 권장

온라인 카탈로그의 목적이 “항상 최신인 작품을 검색하고 바로 읽기”라면 Pupil식 원격 검색형을 우선한다. 이 경우 VCK 전체 DB 설치와 신규-ID 증분 갱신은 제거할 수 있다. 반대로 “한국어 전체 카탈로그를 네트워크 없이 검색”해야 한다면 Pupil은 상세 조회·이미지 URL·지연 캐시 구현의 참고 자료로만 사용하고 로컬 카탈로그형을 유지한다.

#### 사용자 결정 — 원격 검색형 채택

사용자에게 중요한 것은 온라인에서 최신 작품을 즉시 검색·열람하고 북마크하는 경험이며, 전체 카탈로그의 오프라인 검색은 우선순위가 아니다. 로컬 파일 사용량도 줄이고 싶다. 따라서 다음 방향을 제품 요구로 확정한다.

- Hitomi 원격 index를 기본 검색·정렬·태그 필터 데이터로 사용한다.
- 검색 결과 ID의 상세 metadata와 페이지 목록은 사용자가 열 때 지연 조회한다.
- 북마크와 읽기 진행도는 작은 Lakomics 로컬 DB에 영구 저장한다.
- 전체 원격 카탈로그 DB, VCK 초기 가져오기, 신규-ID 전용 로컬 갱신 작업은 최종 구조에서 제거한다.
- 표지, 상세 metadata, 페이지 이미지는 영구 소장 데이터가 아니라 크기 제한과 자동 정리 정책이 있는 캐시로 취급한다.
- 캐시 삭제가 북마크와 읽기 진행도를 지우면 안 된다.
- 네트워크 오류 시 북마크 목록과 진행도는 유지하되, 캐시에 없는 작품은 온라인 연결이 필요하다고 명확히 표시한다.
- 기존 `catalogs/kdata.db`, 검색 제안, 태그 번역 파일은 새 원격 검색 경로가 검증된 뒤 제거 대상으로 다룬다. 요구사항 수집 단계에서는 삭제하지 않는다.

#### 마이그레이션 주의

- 기존 온라인 카탈로그 북마크는 provider와 gallery ID를 유지한 채 새 원격 검색 결과와 연결해야 한다.
- 읽기 진행도와 이미지 캐시는 서로 다른 생명주기를 가져야 한다.
- 기존 로컬 카탈로그를 먼저 삭제한 뒤 새 원격 검색을 시험하는 순서는 금지한다.
- 원격 검색, 상세 조회, 이미지 URL 계산이 검증된 뒤 기존 카탈로그 파일을 제거하고 회수 용량을 사용자에게 알려야 한다.
- Pupil 구현을 참고하되 Lakomics의 Rust Module 경계, 요청 제한, 오류 모델, 기존 미디어 프로토콜에 맞춰 독립적으로 구현한다.

#### 사용자 결정 — 512MB 자동 캐시

- 온라인 카탈로그 캐시의 기본·고정 상한은 512MB로 한다.
- 캐시에는 원격 작품 metadata, 표지/썸네일, 열람한 페이지 이미지를 포함한다.
- 상한을 넘으면 최근 사용 시각을 기준으로 오래 사용하지 않은 캐시부터 자동 정리한다.
- 현재 열람 중이거나 다운로드가 진행 중인 파일은 정리 대상에서 제외한다.
- 북마크, 읽기 진행도, provider gallery ID는 캐시가 아니며 자동 정리 대상이 아니다.
- 사용자는 설정에서 현재 캐시 사용량을 확인하고 전체 캐시를 즉시 비울 수 있다.
- 캐시 전체 삭제 후에도 북마크 목록과 읽기 진행도는 그대로 남아야 한다.
- 초기 구현에서는 캐시 용량 선택 옵션을 추가하지 않는다. 실제 사용에서 512MB가 부족하다는 근거가 생길 때만 설정 범위를 확장한다.

## 2. 상단바의 안정적인 정보 구조

### 사용자 관찰

에셋 등을 클릭할 때마다 상단바 내용물이 바뀌어 위치와 기능을 예측하기 어렵다. 일부 기능을 우클릭 컨텍스트 메뉴로 옮기고 상단바에는 일정한 내용만 유지하고 싶다.

### 현재 구현 확인

- 공통 `ViewToolbar`는 제목, 화면별 내용, 화면별 액션, 창 제어 버튼을 한 줄에 조합한다.
- 여러 화면이 선택 상태나 현재 보기 문맥에 따라 서로 다른 컨트롤을 주입한다.
- 공통 컨텍스트 메뉴가 이미 있으며 Collection 카드의 편집, 쇼케이스, 삭제 등에 사용된다.
- 디자인 기준은 툴바에 현재 위치와 문맥상 필요한 조작을 두고, 선택 모드에서는 일반 탐색 도구를 선택 작업으로 교체하도록 정하고 있다.

### 비판적 판단 — 수정 수용

상단바가 클릭마다 크게 재배치되는 현상은 위치 기억을 깨므로 개선 가치가 높다. 다만 상단바를 완전히 불변으로 만들거나 모든 선택 명령을 우클릭에만 숨기면 발견성과 키보드 접근성이 나빠진다. 특히 우클릭은 유일한 명령 경로가 되어서는 안 된다.

### 권장 방향

- 상단바의 **골격과 슬롯 위치**를 고정한다: 화면 제목, 화면 범위/검색, 보기 설정, 창 제어.
- 개별 에셋에만 적용되는 편집·분류·삭제 같은 명령은 컨텍스트 메뉴로 이동한다.
- 자주 쓰거나 다중 선택에 필요한 핵심 명령은 고정 폭의 선택 액션 영역 또는 단축키/명령 메뉴에도 제공한다.
- 선택 상태 변화는 컨트롤 전체의 삽입·삭제보다 활성화/비활성화, 개수 표시, 고정 슬롯의 내용 교체로 표현한다.
- 실제 이동 대상은 화면별 툴바 명령 목록을 먼저 조사한 뒤 결정한다.

### 완료 기준 초안

- 에셋을 선택하거나 선택 해제해도 제목, 검색/범위, 보기 설정, 창 제어의 위치가 움직이지 않는다.
- 항목 전용 명령은 해당 항목의 컨텍스트 메뉴에서 사용할 수 있다.
- 우클릭 없이도 키보드 또는 명시적인 메뉴로 같은 핵심 명령에 접근할 수 있다.
- 다중 선택 상태와 적용 대상 수가 분명하게 보인다.

## 3. Collection 유형 탐색 단순화와 게임 캐릭터 제외

### 사용자 관찰

Collection의 `전체` 탭을 삭제하고 싶다. 게임과 게임 캐릭터가 합쳐져 있는데, 게임 캐릭터는 우선 모두 제외하고 싶다.

### 현재 구현 확인

- Collection 유형은 `게임`, `만화`, `영화` 세 가지뿐이며 `전체`가 이들을 한 화면에 혼합한다.
- 최신 Works/Collection 제품 기준은 혼합 `전체` 갤러리를 사용하지 않고 유형별 탐색만 제공하도록 이미 결정되어 있다.
- Collection 진입과 상세 화면 종료 경로는 현재 `typeFilter: null`인 전체 보기로 돌아간다.
- 레거시 책 데이터 가져오기에서 `Type=gacha`는 `game`으로 변환된다. 현재 Collection 유형만으로는 일반 게임과 이 레거시 게임 캐릭터 데이터를 다시 구별할 수 없다.

### 비판적 판단

#### `전체` 탭 삭제 — 수용

기존 제품 결정과 일치하며, 서로 다른 표지 비율과 상세 동작을 한 화면에 섞는 문제도 줄인다. 단순히 탭 버튼만 지우면 `typeFilter: null` 경로와 `전체 쇼케이스`가 남으므로 진입 기본값, 마지막 사용 유형 복원, 상세 화면 종료 위치, 쇼케이스 유형 분리까지 함께 정해야 한다.

#### 게임 캐릭터 제외 — 수정 수용

사용자가 제외하려는 게임 캐릭터는 레거시 원본에서 `Type=gacha`였던 항목으로 확인됐다. 방향은 명확하지만 현재 저장 모델에서는 일반 게임과 `gacha` 출신 항목이 모두 `game`이다. 제목이나 폴더명 추측으로 숨기거나 삭제하면 실제 게임을 잘못 제외할 위험이 크다. 원본 `Type` 또는 동등한 provenance를 복구해 비파괴적으로 숨기는 방식이 안전하다.

### 권장 방향

- Collection 진입 시 마지막으로 본 유형을 복원하고, 기록이 없으면 `게임`, `만화`, `영화` 중 명시적으로 정한 기본 유형을 연다.
- 일반 Collection과 Showcase 모두 유형별 보기만 제공한다.
- 게임 캐릭터는 데이터 삭제 없이 목록과 검색에서 제외한다.
- 안정적인 출처/종류 표지가 없다면 레거시 데이터에 `legacy_kind` 또는 동등한 provenance를 보존·보강한 뒤 필터링한다.
- “게임 캐릭터”가 향후 독립 유형인지, 태그인지, 완전히 지원하지 않을 데이터인지 결정하기 전에는 새 Collection 유형을 추가하지 않는다.

### 완료 기준 초안

- Collection 화면에 혼합 `전체` 탭과 `전체 컬렉션` 보기가 없다.
- Collection 진입 및 상세 화면 종료 시 결정된 유형 화면으로 일관되게 이동한다.
- Showcase도 게임·만화·영화가 섞인 전체 보기를 만들지 않는다.
- 식별된 게임 캐릭터 항목은 기본 목록과 검색 결과에 나타나지 않는다.
- 제외 과정에서 Collection 레코드나 연결된 자산은 삭제되지 않는다.

### 확정 사항과 미결정 사항

- “게임 캐릭터”는 레거시 원본에서 `Type=gacha`로 분류됐던 항목을 뜻한다.
- 게임 캐릭터를 데이터에서 영구 삭제할지, 보존하되 UI에서 숨길지는 결정이 필요하다.
- 마지막 사용 유형 기록이 없을 때 기본 진입 유형을 정해야 한다.

## 제안 우선순위

1. **P1 — Collection `전체` 제거와 안전한 게임 캐릭터 식별/숨김**: 최신 제품 결정과 맞지만 데이터 식별 문제를 먼저 풀어야 한다.
2. **P1 — 상단바 안정화**: 전 화면에 걸친 UX 문제이므로 명령 목록 조사와 공통 슬롯 설계가 선행되어야 한다.
3. **P2 — 카탈로그 관리 경로 정비**: 실제 갱신 기능은 존재하므로 기능 신설보다 발견성, 상태 표시, 교체/복구 경로를 보강한다.

우선순위는 사용 빈도와 현재 불편의 강도를 더 확인한 뒤 조정한다.
