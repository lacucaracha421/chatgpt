# Server-owned release wishlist contract (2026-10-09)

Status: audited proposal at `main`, `d7d16d48305a8a11c139f20463c93a5ea5fc1e3a`; design only.
Scope: game/movie/anime interest, intent application, per-title dates and events. No Collections release checks, Kakao binding or MangaDex changes.
Source references below are repository-relative `file:line` anchors; statements in target sections are proposed requirements, not implemented behavior.
The user's report that the calendar switch is ON in production is context, not independently verified here. No network, provider, production/library access, installs or test suites were used.

## 1. Current flows and authority

### Tablet and server

- Calendar add/remove: clicking changes a connection-scoped localStorage outbox, retaining one UUID per desired action across retries; an opposite click supersedes it. POST carries version 1, operationId, action and itemId. Only a later GET matching membership clears the outbox (`_tools/app/mobile-client/ReleaseCalendar.tsx:222`; `_tools/app/mobile-client/upcomingWishlistOutbox.ts:12`, `:30`, `:41`, `:58`).
- Home uses the same outbox, flushes before reading `/v1/home/upcoming`, and overlays pending local membership (`_tools/app/mobile-client/homeDashboard.ts:247`). Calendar parses server `pending` but its visible membership overlay uses the local outbox (`_tools/app/mobile-client/releaseCalendarModel.ts:123`, `:142`; `_tools/app/mobile-client/ReleaseCalendar.tsx:213`). Do not assume every pending action has a visible control.
- Acknowledge sends one exact event ID with a fresh UUID, then removes that event from displayed unread rows on POST success; failure displays an error. This path has no persistent ACK outbox (`_tools/app/mobile-client/ReleaseCalendar.tsx:230`).
- Mute/unmute are accepted API actions, but the audited tablet calendar has toggle and acknowledge handlers, no mute controls (`server/lakomics-api/home_upcoming.py:226`; `_tools/app/mobile-client/ReleaseCalendar.tsx:222`, `:230`, `:299`). API path: POST -> ordered log -> PC -> later snapshot, just like remove; this is not an implemented tablet mute UX.
- Server authenticates client POSTs, validates UUID/action/event IDs, replays matching receipts, rejects reused UUIDs with changed bodies, then appends a monotonically sequenced intent. Unknown item IDs require a published ID or pending intent; pending limit is 500 (`server/lakomics-api/home_upcoming.py:387`, `:404`, `:410`, `:431`, `:445`). Arbitrary manual IDs cannot use this existing route today.
- Add captures public Title data from the current wishlist/calendar, or a previous add intent; legacy log rows fall back to current publication on intent reads (`server/lakomics-api/home_upcoming.py:250`, `:417`, `:473`). The server currently does not fetch or apply wishlist changes.
- GET returns the stored wishlist plus unacknowledged intents in sequence order, revision, acknowledgedThrough and ETag/304. The PC reads the publisher-only paged intent route; acknowledged log retention is 30 days / newest 5000, receipts newest 2000 (`server/lakomics-api/home_upcoming.py:91`, `:261`, `:365`, `:456`). Server storage includes document/digest/revision, known IDs, log head/ACK/prune cursors, captured titles and receipts (`server/lakomics-api/home_upcoming.py:108`, `:124`).

### PC editing and intent application

- PC `ReleaseCalendarView` loads wishlist through the gateway; bookmark add/remove and individual/all-event confirmation call gateway mutations then reload wishlist and update badges (`_tools/app/src/collections/ReleaseCalendarView.tsx:85`, `:151`, `:164`, `:252`, `:296`). Tiles derive watched membership from wishlist IDs (`_tools/app/src/collections/ReleaseCalendarView.tsx:126`, `:143`).
- Gateway invokes Tauri list/add/remove/mute/ACK/run commands, which call Library methods (`_tools/app/src/library/client.ts:268`; `_tools/app/src-tauri/src/commands/release_calendar.rs:104`). Manual IDs and mute are native/gateway capabilities; these calendar UI handlers expose neither a manual-ID input nor mute action (`_tools/app/src/collections/ReleaseCalendarView.tsx:151`; `_tools/app/src/library/client.ts:269`, `:271`). Preserve capabilities without inventing new controls in this migration.
- Add validates canonical positive numeric IDs: `igdb:<id>`, `tmdb:<id>`, `tmdb:tv:<show>:s<season>`; no zero-padding. It prefers the server calendar title when calendar ownership is enabled, otherwise local cache; cache miss fetches the provider as source `manual` (`_tools/app/src-tauri/src/library/release_wishlist.rs:133`, `:329`).
- Insert is membership-idempotent: existing row unchanged. New membership stores dates as baseline, emits no events, initializes schedule and released_at if already released. Calendar port adds freeze the selected platform labels; manual/non-port adds leave tracked scope null (`_tools/app/src-tauri/src/library/release_wishlist.rs:240`).
- Remove deletes membership; child dates/events cascade. Mute only flips a flag; ACK marks exact unread IDs read. Mutations signal upcoming publication (`_tools/app/src-tauri/src/library/release_wishlist.rs:282`, `:301`, `:366`; `_tools/app/src-tauri/migrations/0098_release_calendar.sql:53`, `:67`). PC bulk ACK is not item-scoped; tablet-intent ACK is.
- Publication polling reads up to three validated pages per pass, applies each page and saves its cursor in one local transaction. Replayed pages do nothing (`_tools/app/src-tauri/src/library/home_publications.rs:295`, `:497`).
- Intent add uses captured public Title or local cache, with server-calendar mode preferring captured Title; no provider call. Public Title reconstructs one headline date per platform, not all provider dates. Malformed/missing titles may become acknowledged no-ops. Remove/mute unknown membership are no-ops; ACK filters IDs by item ownership (`_tools/app/src-tauri/src/library/home_publications.rs:519`; `_tools/app/src-tauri/src/library/server_release_calendar.rs:363`, `:405`). These are the current H1 fix and its limits, not the older calendar document's unfixed cache-only behavior.
- Cursor advances for every handled intent; later PUT acknowledges it on the server. With server calendar enabled PC publishes `wishlistOnly:true`, preserving the calendar; otherwise it publishes a full document (`_tools/app/src-tauri/src/library/home_publications.rs:558`, `:413`; `server/lakomics-api/home_upcoming.py:301`, `:319`). Publication builds every ten minutes or on changed inputs, suppresses unchanged digest writes, and backs off failures from 60 seconds up to one hour (`_tools/app/src-tauri/src/library/home_publications.rs:20`, `:259`, `:359`, `:390`).

### Provider checks, dates and events

- The PC startup/hourly hook runs wishlist due checks unless workload is restricted, even with server calendar ON (`_tools/app/src/app/useReleaseWatchCheck.ts:5`, `:14`, `:60`, `:69`). Rust runner selects unmuted rows with non-null due next_check_at, ordered by next_check_at/id, first 40; IGDB batches ten, followed by individual movie/anime fetches (`_tools/app/src-tauri/src/library/release_wishlist.rs:520`, `:547`, `:566`).
- Success schedule: 24 hours ordinarily; exact dates at most 14 days away use six hours, including past dates through day +30; stop only when more than 30 days past. Coarse/TBD dates never age-stop. Unmute does not reset next_check_at (`_tools/app/src-tauri/src/library/release_wishlist.rs:77`, `:288`, `:648`).
- Live wishlist transport uses PC OS credentials and raw IGDB/TMDB clients, not server relay normalization (`_tools/app/src-tauri/src/library/release_calendar.rs:222`; `_tools/app/src-tauri/src/library/igdb.rs:171`; `_tools/app/src-tauri/src/library/tmdb.rs:226`). Server relay already has server credential access (`server/lakomics-api/work_providers.py:203`, `:215`).
- IGDB ID query uses calendar fields without discovery popularity/window filters. Parsing prefers major-platform dates, falling back to all platforms only if none survive; excludes add-ons, keeps earliest region/platform dates and Korean title when available (`_tools/app/src-tauri/src/library/release_calendar.rs:658`, `:703`, `:521`). Port scope filters against frozen labels and recomputes headline; empty scope keeps previous metadata/dates (`_tools/app/src-tauri/src/library/release_wishlist.rs:220`, `:617`).
- Movie detail is `/movie/<id>?language=ko-KR&append_to_response=release_dates`; earliest KR theatrical type 2/3 precedes primary worldwide date. Anime reads Korean TV detail and the requested positive season; undated seasons remain trackable, title/poster fallback follows the season rules (`_tools/app/src-tauri/src/library/release_calendar.rs:744`, `:896`, `:918`, `:983`, `:995`). No discovery-window restriction on per-title checks.
- Headline prefers Korea -> Asia -> worldwide -> earliest elsewhere; earliest period start, precise on ties. Event values encode exact/month/quarter/year/TBD tokens (`_tools/app/src-tauri/src/library/release_calendar.rs:276`, `:290`).
- Changed tokens emit date_set for TBD becoming dated or a period narrowing to an exact day inside it; otherwise date_changed. Exact date reached emits released once. released_at is a monotonic latch even if dates later move into the future (`_tools/app/src-tauri/src/library/release_wishlist.rs:100`, `:632`, `:645`).
- Provider calls occur outside the DB lock. On apply, deleted membership is ignored; previous headline is read inside the transaction. Successful metadata updates retain the old cover when new cover is absent, replace dates, insert random-UUID events, update schedule and signal publication (`_tools/app/src-tauri/src/library/release_wishlist.rs:190`, `:596`).
- Missing IGDB result or TMDB 404/missing season retains prior dates, still detects released against that baseline and updates the normal schedule: potentially six hours, despite the comment saying tomorrow. Other failures leave due state unchanged, stop that provider lane and preserve first error; the other provider still runs. There is no persisted wishlist failure backoff (`_tools/app/src-tauri/src/library/release_wishlist.rs:547`, `:578`, `:625`, `:648`).
- Native local calendar watched flags also query local membership; server-calendar adapter does the same (`_tools/app/src-tauri/src/library/release_calendar.rs:1204`; `_tools/app/src-tauri/src/library/server_release_calendar.rs:653`). Calendar ownership alone has not moved wishlist ownership.

## 2. Target ownership and client contract

- Server owns membership, baseline dates, scope, mute, read history, release latch, schedule, ordered intent application and provider event detection. PC retains cached display, connection credentials and durable outgoing requests; no authoritative wishlist writes/checks after activation.
- Keep existing tablet POST exactly unchanged. Apply accepted actions in server sequence order and atomically publish wishlist + acknowledgedThrough + revision; a successful POST may finish application immediately. Pending remains the unapplied suffix. Never advance ACK before domain state and projection commit.
- A provider-independent applier drains up to 200 intents / two seconds per transaction, after POST and on startup/wake while server-owned and ON; a bounded continuation resumes any suffix. Require contiguous sequence above appliedThrough; any gap blocks visibly. Check receipts before membership/known-ID validation, retaining the current 2000-receipt replay window (§1); handover receipts have separate durable retention. Validate new adds against 1000-item/document caps before acceptance where possible; never trim membership to fit a publication.
- Add uses captured Title as baseline (including headline-per-platform reconstruction parity) without network; duplicate add unchanged. Preserve source `calendar`, freeze platforms for port adds, and emit no initial events. Legacy titleless intents need current publication fallback; unresolved add must stop the prefix and expose an error, not silently disappear. Remove/mute of missing membership and unknown/non-belonging ACK IDs remain safe no-ops.
- All new PC wishlist commands route to server client-authenticated POSTs through Rust, with durable UUID requests and retry of the same payload; read through the authoritative projection/cache. ACK-all groups exact event IDs by item (at most 100 per request). Confirm success by a later GET; update watched flags and badges from server membership plus local pending requests.
- Preserve native manual-ID ability through a new client-authenticated `/v1/home/upcoming/wishlist/manual` endpoint: version, operationId, canonical itemId. It resolves provider data outside locks, then appends an add in the same ordered log with stored full baseline/source `manual`. Receipt lookup precedes fetch; recheck receipt and ownership on commit. Concurrent duplicate requests cannot create duplicate membership or events.
- Do not repurpose existing known-item POST validation or accept arbitrary client-supplied provider dates. Manual request failures leave no accepted intent; duplicate existing membership needs no fetch. Enforce published-ID length bounds and canonical numeric identities explicitly; reject unsupported values rather than renaming IDs.
- Rust gates every mutation/check/publication entry point, not only the hourly hook. UI keeps the current controls and previous content during refresh. Calendar refresh and wishlist checks have separate status/run APIs; a dead provider worker must not disable server-owned membership edits.

## 3. Server tables, seeding and publication

Proposed plain SQLite tables (existing home_upcoming log/receipts/state remain the shared wire store):

| Table | Key and required fields |
| --- | --- |
| release_wishlist_owner | singleton; mode (`server`/`transferringToPC`/`pc`), ownerEpoch, libraryId, endpoint provenance, seedOperationId/digest, seedCursor, appliedThrough, stateRevision, currentProjectionDigest. Epoch changes fence writers and in-flight checks. |
| release_wishlist_handover_receipts | operationId PK; payloadDigest, direction, epoch, result, frozen export digest/cursor for reverse transfer. Persist across restarts/epoch changes; never prune with ordinary intent receipts. |
| release_wishlist_items | stable id PK; kind/provider/external_id unique; raw metadata/cover, platforms_json, nullable tracked_platforms_json, source/added_at/muted, last_checked_at/next_check_at/released_at; membershipGeneration, itemRevision, checkRevision. |
| release_wishlist_dates | (item_id, region, platform) PK; date/precision/checked_at; FK cascade, TBD/null consistency. |
| release_wishlist_events | event id PK; item_id FK cascade; kind/previous/current/detected_at/read_at; unique (membershipGeneration, checkRevision, ordinal) for server-generated events. Imported IDs remain exact. |
| release_wishlist_provider_state | upstream (`igdb`/`tmdb`) PK; attempted_at, failures, error_code, retry_at, next_lane; TV shares TMDB quota/backoff. |
| release_wishlist_status | singleton; alive/busy/draining, wake times, checked/changed/remaining, stopReason, blocked sequence, publication error. No secrets/provider bodies. |

Indexes follow due/unread access. Full-baseline add data extends internal log storage only. Membership generation changes on re-add so stale fetches cannot recreate deleted interest. No new shared event API or Collections entity is needed.

### One-time ownership handshake

1. Dormant slice creates tables only; no existing wishlist seed, log application or projection writes while switch OFF. With switch ON but unseeded, remain `awaitingSeed`, no wishlist feature advertisement/checks. Explicit empty seed is valid; absence of seed is not an empty list.
2. New PC quiesces local wishlist commands/checks and upcoming publication, joins in-flight operations, then captures all three tables and endpoint cursor in one transaction. Ordinary edits during transfer remain queued with stable operation IDs, not locally applied. Read current server revision/digest/ACK/head and prepare publisher-authenticated `/wishlist/handover` with version, UUID, expected revision/digest, library identity, cursor C and lossless rows.
3. Under BEGIN IMMEDIATE, validate credentials/provenance, switch, unowned/current epoch, expected server revision/digest, `acknowledgedThrough <= C <= intent_sequence`, schema/IDs/FKs/caps and full snapshot integrity. CAS failure retries from fresh reads; never force replacement. A newer server ACK than C requires PC catch-up before a new seed.
4. Import exact membership, raw dates/scope/times and all read/unread events, recording C as appliedThrough and ACKing through C: the PC seed already includes those intents. Do not replay them. Apply pending C+1 onward strictly in order; use stored title/legacy fallback rules. Import itself produces no synthetic events or fresh provider checks.
5. Commit imported state, owner epoch, public projection, ACK/revision, cover refs, known IDs and handover receipt together. Preserve latest calendar/range/sources. Any failure rolls all back; duplicate UUID + same digest returns the durable receipt; different digest conflicts. Same epoch never accepts another seed, even after restart or switch OFF.
6. PC persists confirmed server ownership, discards seed transport retry state and sends queued edits to server. Lost response probes/retries the same handshake; local writers remain quiesced until receipt or a definitive no-transfer result. Another PC cannot auto-seed over an owner. Server schema persists across switch changes; never rerun backfills or replace the catalog DB.

Seed body must be separately bounded and validated; public 50-event truncation must not truncate migration history. Oversized seed fails explicitly before ownership changes; bounded staged transfer, if needed, is a later contract decision, not an excuse for partial import. No production counts were inspected.

### Existing tablet bytes and calendar coexistence

- Freeze public keys: Title `id,kind,title,originalTitle,date,precision,region,platforms,releaseType,cover,popularity,port` plus wishlist `source,addedAt,muted,released,events`; event keys `id,kind,previousValue,currentValue,detectedAt,readAt`. Keep popularity null, port false and releaseType null in wishlist as PC publishes today (`_tools/app/src-tauri/src/library/home_publications.rs:155`, `:419`; `server/lakomics-api/home_upcoming.py:160`, `:184`). Internal tracked scope never depends on public port.
- Preserve item order `(date absent, date, title, id)`, unread event order `(detected_at,id)`, newest 50 unread events per item, text/control/character limits and cover validation; preserve imported public values, IDs and timestamps (`_tools/app/src-tauri/src/library/release_wishlist.rs:430`, `:493`; `_tools/app/src-tauri/src/library/home_publications.rs:112`, `:125`, `:426`).
- Use the existing sorted-key compact Unicode encoder, version 1 envelope, caps (1000 wishlist / 8 MiB document), ETag and signals. No worker fields in public rows. Pin literal canonical wishlist bytes for identical inputs; live generatedAt/publishedAt/revision naturally change with real writes (`server/lakomics-api/home_upcoming.py:91`, `:135`, `:365`).
- A publication transaction reloads latest document and changes only the owned segment; refresh cover refs and known IDs for both segments. Domain/ACK commits require valid projection; no snapshot/revision churn for unchanged checks. Provider I/O stays outside DB locks; bounded failed publication records status separately and retries from retained result, not a refetch loop.
- If a worker result is retained for publication retry, it is bounded and tagged with expected owner/item/check revisions; revalidate before applying. Successful checks advance private schedule/status only when public content stays identical. Missing-title success is not a provider failure; newly reached release day is still a semantic change.
- Existing calendar ownership is a whole-document digest fence, not a calendar-only digest. Calendar store preserves wishlist but checks that digest; legacy full PUT deletes its owner row (`server/lakomics-api/release_calendar.py:490`; `server/lakomics-api/home_upcoming.py:325`). Every wishlist publication must advance the calendar owner's digest in the same transaction if it exists, or the next calendar wake will stop publishing. Calendar and wishlist writers must share this merge/fence rule; neither changes the other's cursors/state.

## 4. Per-title worker and shared provider budget

- One daemon, 30-second start delay, ten-minute wakes and bounded on-demand due runs; <=40 titles/wake, IGDB batches <=10, sequential network work. Keep normal 24h/6h/>30-day schedule exactly (§1); server day/timezone selection awaits Q1. Remaining work gets a later wake; persist fair provider rotation when time budget prevents finishing.
- Proposed bounds: 90 seconds/wake, <=40 primary queries and <=48 actual outbound requests including OAuth/401 retries; 20-second/request deadline clipped to wake, five-second socket cap, <=4 MiB/provider response and <=16 MiB aggregate bytes/wake. Cap parsed rows per IGDB batch, validate requested IDs, no artwork downloads. Manual lookup consumes the same upstream pacing, with its own bounded request/response budget.
- Reuse one Relay instance/locks/token cache and next_request spacing with calendar and interactive providers; IGDB 250ms, TMDB 100ms including TV. Existing calendar is 240s/128 queries; these independent wake budgets are not additive provider quota permissions (`server/lakomics-api/release_calendar.py:36`, `:339`; `server/lakomics-api/work_providers.py:162`, `:188`, `:215`). Enforce a shared background arbiter: alternate due workers, release after each request, yield to interactive work, no nested Relay.paced locks.
- Calendar doc M3 identified lock-held pacing causing interactive 429 (`docs/research/server-release-calendar-20261009.md:115`). Current interactive acquisition now waits up to 0.5s, but json_request still sleeps and performs HTTP under the worker-held lock (`server/lakomics-api/work_providers.py:171`, `:188`; `server/lakomics-api/release_calendar.py:344`). M3 is mitigated, not eliminated. Before activation, test contention; reserve pacing safely and sleep outside exclusive work, or a bounded fair queue must prevent consecutive background requests starving interactive callers. Do not introduce separate locks/rate clocks.
- Fetch ID-specific wishlist data, porting §1 parsers rather than work-detail normalizers or calendar discovery. Read membership generation/revision before fetch; under BEGIN IMMEDIATE reload owner epoch and item state. Deleted/re-added/modified membership invalidates the result. Mute/read changes must remain current; discard/retry conservatively on revision mismatch.
- Apply dates/metadata, detect events from the latest baseline, increment checkRevision and derive deterministic event UUIDs from owner epoch + membership generation + checkRevision + ordinal. Commit events/latch/schedule/projection together. Replay/crash cannot duplicate events; genuine A->B->A transitions remain distinct. Never use a permanent content-only event dedup key.
- Missing IGDB row, TMDB 404, missing season or empty tracked-platform scope keeps last dates/metadata, permits released detection from that baseline and uses normal next_check. No auto-delete, silent unwatch or new disappeared event. Invalid responses/network/auth failures do not count as successful checks or overwrite good baseline.
- Failure backoff is an explicit operational addition to PC parity: per-upstream 1h for timeout/unavailable/invalid response/auth; 429 honors bounded Retry-After (at most 24h), otherwise 1h. No sleep loop; other upstream continues. Budget/lock contention yields without counting provider failure or moving title schedule. Success resets failure state; stopped next_check=null stays stopped. Manual run respects due/backoff, no force-refresh product change.
- Client-authenticated `/wishlist/status` separates ownership/seed readiness from worker enabled/configured/alive/busy, lane retry/error and blocked intent. `/wishlist/run` accepts `{}` or version 1, queues due work, max six/client/minute; disabled 404, unavailable worker 503, invalid/large body 422/413, excess 429 with Retry-After. Authentication precedes availability checks. No provider failure should block remove/mute/ACK.

## 5. Switch, old clients and safe fallback

- New `LAKOMICS_RELEASE_WISHLIST` defaults OFF; no thread, requests, intent ACKs or public writes while dormant. ON allows handshake; only completed owner + configured switch advertises `serverReleaseWishlist` through the existing Collections status feature channel (`server/lakomics-api/collection_authority.py:4076`). Keep ownership advertisement stable through draining/dead worker and use status to expose health; credentials gate checks/manual lookup, not established membership authority.
- OFF after handover preserves the owner fence and accepts ordinary tablet intents into the existing pending log without applying them. Authenticated ownership status and publisher recovery/export routes remain available while OFF; only run/manual-provider work becomes unavailable. Restart resumes pending intents before provider checks when ON again.
- Calendar precedent currently advertises with switch + credentials, independently of worker alive; PC requires active feature and waits 180s after observed absence (`server/lakomics-api/release_calendar.py:73`; `_tools/app/src-tauri/src/library/server_release_calendar.rs:16`, `:444`). Do not copy the older design prose's alive-only gate. Wishlist absence must never alone authorize local replacement.
- While server owns wishlist, fence legacy full PUT and wishlistOnly PUT with explicit 409 `serverWishlistOwned` (before cursor validation), retaining server rows/ACK/receipts. Do not return changed:false success for discarded edits. Old PC can still display its stale local wishlist/check locally, but its writes cannot affect shared state; upgrading is necessary to edit correctly. Separate calendar-only publication may be added to the new PC for calendar-local/wishlist-server mode; it never carries wishlist or intentCursor.
- Old tablets continue existing version 1 GET/POST and UUID receipts; server application makes membership visible without PC polling. Keep pending suffix and exact ACK behavior. Muted checks remain skipped. No mandatory tablet upgrade, new manual/mute UI or notification channel in these slices.
- New PC gates intent polling/application, local checks and wishlist PUT once transfer is confirmed. Cache key and durable mode include endpoint/library/owner epoch; errors, offline status, 304 or worker death do not mean ownership disappeared. Missing feature after a confirmed status response triggers status recovery, holding cached UI/outgoing requests.
- For deliberate OFF, drain worker and freeze server application, then use an explicit publisher-authenticated reverse handover with expected epoch/stateRevision. Persist `transferringToPC` and a frozen complete private export/appliedThrough before replying; newly accepted tablet intents remain above that cursor. PC imports atomically while quiesced, then confirms server relinquishment using the export digest/UUID. Resume queued/unapplied intents and ordinary legacy publication only after confirmation. Conflict/lost reply keeps both writers fenced and is receipt-recoverable; no automatic transfer timeout. Resume server only via a new epoch handshake, never stale seed reuse.
- If the server loses the feature/routes entirely, there is no safe automatic lossless fallback from the public snapshot. Keep cached read/offline queue and explain recovery is needed; do not overwrite server history from pre-handover PC tables. Q5 asks whether this safety-first degraded mode is acceptable. Calendar fallback remains separately governed; its fresh-local-cache fence exists today (`_tools/app/src-tauri/src/library/server_release_calendar.rs:472`; `_tools/app/src-tauri/src/library/home_publications.rs:332`).

## 7. Risks and open product questions

Risks: incomplete seed loses port/date/history state; stale PC writes erase server actions; whole-document calendar digest can strand calendar updates; log gaps block ordered application; provider lock contention starves interactive lookup; snapshot/event caps exceed private transfer limits. These are acceptance gates, not permission to discard data.

1. **Timezone:** should server release detection use Asia/Seoul (calendar uses fixed UTC+09:00, `server/lakomics-api/release_calendar.py:604`) or a configurable library timezone? PC currently uses OS-local day (`_tools/app/src-tauri/src/library/release_wishlist.rs:505`); no choice made here.
2. **Mute/stop semantics:** retain pause-checks-on-mute, six-hour checks through day +30, and permanent stop after day +30? Should unmute or a later postponement restart a stopped title? Current behavior is audited in §1; no new policy selected.
3. **Release latch:** retain one released alert for membership lifetime even after postponement, or allow another released alert when the new date arrives? Parity tests must pin today's latch until a change is approved.
4. **Unavailable titles:** keep last known dates indefinitely with normal checks, or eventually show an unavailable state/change cadence? Today's missing-title behavior is the proposed parity baseline, not a new disappearance policy.
5. **Rollback/old PC:** accept cached read + queued edits until explicit reverse handover when the feature vanishes, and require old PCs to upgrade for shared edits? Automatic fallback cannot preserve private state from the public snapshot.
6. **Offline/manual/mute UX:** should PC offline edits be visible immediately as pending, and should either client gain manual-ID or mute controls? Server migration preserves existing native capabilities; new visible controls are not included without a decision.
7. **History/large migration:** retain all server read-event history as the PC does, and support bounded staged seed if it exceeds a single upload limit? No production size/count or desired retention was confirmed.

## 8. Controller decisions (2026-10-09)

Single user, one PC, wishlist of 16 items at the time of writing. These decisions simplify §§2-6 and override them where they conflict:

- **Q1-Q4, Q6, Q7: parity.** Release day uses the fixed UTC+09:00 day like the calendar (the PC's OS-local day is KST today). Mute, schedule, stop after day +30, the released latch, missing-title handling and full read-event history stay exactly as on the PC. No new UI controls (manual ID, mute) in these slices.
- **No manual-ID endpoint.** No UI exposes manual IDs; the PC gateway keeps its native command but it is not exposed after handover. Revisit only when a control is designed.
- **No reverse handover protocol.** Rollback = switch OFF: the server stops applying intents and checks but keeps its rows and the owner fence, so tablet intents queue in the existing log. A recovery export route (read-only GET of the private rows) is part of slice 1; an import into the PC is written only if rollback is ever actually needed. Q5 is accepted as written (safety-first degraded mode).
- **One-shot seed, no staged transfer.** One bounded publisher PUT; an oversized seed fails before ownership changes.
- **Events use random UUIDs** inserted in the same transaction as the check result, schedule and projection; drop membershipGeneration/checkRevision-derived IDs. Keep a per-item revision that a check result must match on commit (deleted or re-added membership discards the result).
- **No ownerEpoch beyond a single owner row** (mode `awaitingSeed`/`server`, seed operationId + digest, appliedThrough). A second seed is refused once owned.
- **Provider budget:** reuse the calendar's Relay and pacing; wishlist checks run in the same daemon thread as the calendar worker or strictly after it, never concurrently, so there is no new lock arbitration. M3 (interactive 429 under worker pacing) is fixed in slice 1 by sleeping outside the provider lock.
- **Keep:** ordered intent application with ACK only after commit, 409 `serverWishlistOwned` fence on PC wishlist PUTs once owned, the calendar owner digest advanced in the same transaction as every wishlist publication, frozen public bytes, and the default-OFF switch `LAKOMICS_RELEASE_WISHLIST` with `serverReleaseWishlist` advertised only when owned and switched on.

Audit limits: source and the two dated design references only; production switch/keys/quotas, wishlist size, deployed builds and real provider deletion behavior unconfirmed. ## 9. Slice 1 implementation notes (2026-10-09)

Implementation is dormant server code only. `LAKOMICS_RELEASE_WISHLIST` remains default OFF; no deployment, switch change, live provider request, production/library access, dependency installation or Git write was performed. ### Implemented server contract

- `server/lakomics-api/release_wishlist.py` contains a standard-library core, startup-only private DDL, a singleton `awaitingSeed`/`server` owner, private items/dates/all events, monotonic item revisions, provider backoff and worker status. A persistent owner revision allocator prevents deleted/re-added membership from reusing a revision. Server-generated events use random UUID v4 inside the result/projection transaction. Imported event IDs, read history, raw dates, serialized scopes and timestamp strings are preserved.
- Publisher `PUT /v1/home/upcoming/wishlist/handover` takes exactly `version`, `operationId`, `expectedRevision`, `expectedDigest`, `libraryId`, `endpoint`, `intentCursor`, `items`, `dates`, `events`. Version is 1; operationId is a canonical UUID. Private rows use the PC SQLite column names (`release_watch_items`, `release_watch_dates`, `release_watch_item_events`), including `platforms_json`, nullable `tracked_platforms_json`, `event_kind` and `checked_at`. Item revisions are assigned by the server and are not seed inputs. The publisher supplies library/endpoint provenance; there is no independent configured library identity in this API against which to authenticate those strings. Publisher authentication, document CAS and the permanent owner fence are the authority checks in this slice.
- The seed is one bounded request: 16 MiB, at most 1000 items and 100000 rows each for dates/events. Raw title/original/event strings allow 10000 characters, cover 4096, and scope/platform arrays 32 labels of at most 1000 characters each. Oversized or invalid seeds fail explicitly; there is no partial import or history truncation. All foreign keys, duplicate keys, canonical numeric provider identities, date/precision consistency and timestamps are validated. Public projection uses the existing stricter wire limits. These numerical private-transfer limits are implementation choices because the contract did not select them; real production sizing remains unverified.
- Seed CAS, imported rows, initial projection, calendar digest fence, cursor ACK and durable UUID receipt commit together. The imported cursor is not replayed; the ordered suffix is applied in a bounded pass, with later continuation on the shared wake. Matching seed retries return the original receipt; changed payloads conflict; another seed is refused once owned. No provider fetch or synthetic event is performed by import.
- Publisher `GET /v1/home/upcoming/wishlist/export` is a consistent read-only export of the complete private rows, owner/receipt, provider state and retained worker state. It stays available while OFF. Client `GET .../status` also stays available while OFF, reporting ownership/readiness, current document revision/digest, log/ACK/application cursors, worker health, provider retry/error state and blocked intent. Client `POST .../run` accepts `{}` or `{"version":1}`, queues due work only, and applies the existing six-per-client-per-minute limiter. Authentication precedes availability checks.
- Existing tablet POSTs retain their original log and UUID receipts. ON/owned POSTs trigger a provider-independent ordered pass (200 intents/two seconds), and startup/wakes resume pending work. Titleless/unresolvable adds and sequence gaps expose blocked status without advancing that prefix. Adds capture a baseline, freeze port platforms and emit no initial events; remove/mute/unmute/exact item-scoped ACK follow the PC rules. ON/owned add admission accounts for pending membership changes and public size before accepting an over-cap add where possible. Publication/cover failures roll back domain and ACK state, with status recorded separately.
- Projection preserves the PC public keys, raw-item sorting, newest 50 unread events in ascending `(detected_at,id)` order, sanitization/cover rules and sorted-key compact Unicode JSON. Private check timestamps and revisions do not churn public bytes. Wishlist publications merge the latest calendar and advance an existing calendar owner digest in the same transaction. Calendar publications continue to preserve wishlist and cursors. Established ownership rejects PC full/wishlistOnly PUTs with `409 serverWishlistOwned` before body/cursor checks, including while OFF.
- The wishlist lane is attached to the existing calendar daemon, after each calendar pass; no second daemon or separate provider locks/rate clocks are introduced. OFF adds no worker start or intent/check application. ON without credentials can still apply membership intents. The lane uses fixed UTC+09 days, up to 40 titles, IGDB batches of ten, ID-specific IGDB/movie/TV detail parsing, port filtering, missing-title baseline retention, precision events and the release latch. Checks use 24h/6h/+30-day stop parity; coarse/TBD do not stop and unmute does not restart a stopped schedule.
- Wishlist provider work uses 90 seconds, 40 primary queries, 48 actual outbound requests including OAuth/401 retries, the calendar's 20-second clipped request deadline/five-second socket cap, 4 MiB responses and 16 MiB aggregate successful response bytes. Provider lanes rotate across wakes. Timeout/auth/invalid/unavailable failures back off one hour; 429 respects bounded numeric or HTTP-date Retry-After up to 24 hours. Contention/budget yields do not move schedules or set provider failure. Failed publication results persist for retry, tagged with the expected item revision; at most 40 results, each capped at 384 KiB, keep retained data below 16 MiB. An unusually large parsed result fails as invalid_response before schedule/domain changes. This parsed-result cap is an additional explicit resource bound.
- M3 is fixed in the shared Relay: pacing releases the existing IGDB/TMDB lock, then reacquires and rechecks the same rate clock. Thread-local ownership prevents a failed reacquisition from releasing someone else's lock. The OAuth token lock is not held across that yield. Existing StashDB/artwork outer-lock behavior is preserved. `serverReleaseWishlist` is advertised only when seeded and ON, independently of credentials or worker health.
