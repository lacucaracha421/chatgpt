# 이미지 유입과 캐릭터 분류 점검

2026-09-12, 기준 HEAD `baccdcc5ff6d1bc40cac80ea400a3ae9395ba19d`와 현재 작업 파일.

이번 구현은 사이드바의 관리 진입점 통합에 한정한다. 캐릭터 엔진은 진단만 했으며, 아래 개선안은 아직 적용하지 않았다. 실제 라이브러리, 서버, 원본 미디어는 변경하지 않았다. 서브에이전트는 사용하지 않았다.

후속 변경(같은 날 사용자 승인): 아래 내용은 최초 점검 시점의 기록이다. 이후 일반 상위·중간 폴더에 저장한 이미지도 하위 등록 시리즈의 준비된 캐릭터들과 비교하도록 변경했다. 확실한 결과만 캐릭터 소속에 추가하며 원래 분류와 파일은 유지한다. 기존 시리즈 지정, 수동 결정, 오리지널 제외는 유지한다. 현재 정책은 [캐릭터 워크플로 설계](character-classification-quiet-workflow-design-20260911.md)의 인식 범위를 따른다.

## 사용자가 보는 흐름

```text
이미지 가져오기
  ├─ 완전히 같은 파일이 있음 → 기존 자산 사용, 요청한 분류 위치 적용
  ├─ 유사 이미지임 → 유사 검토에서 사용자가 결정
  └─ 새 이미지임 → 선택한 분류에 저장
                        ├─ 미분류·일반 상위 폴더 → 그대로 보관
                        └─ 등록된 시리즈 안 → 해당 시리즈의 캐릭터들과만 비교
                                               ├─ 확실함 → 캐릭터 폴더에도 표시
                                               └─ 애매함 → 원래 시리즈에 그대로 보관
```

캐릭터 폴더에 표시하는 것은 관계를 추가하는 일이다. 파일을 복사하거나 물리적으로 캐릭터별 폴더로 옮기지 않는다. 한 이미지에 서로 다른 인물이 있으면 여러 캐릭터 폴더에 표시될 수 있다.

## 경우별 추적

| 경우 | 실제 경로와 결과 |
| --- | --- |
| PC 파일 선택·외부 파일 드롭 | 현재 `classificationId`를 수집 요청에 저장한다. 수집 성공 시 정상 정지 이미지에만 분류 작업 예약을 시도한다. |
| 확장 프로그램 직접 수집 | 지정한 분류 ID와 함께 동일한 `ingest_media` 경로에 들어온다. 별도의 캐릭터 추측 경로가 아니다. |
| Cloud Capture 수신 | 같은 수집 경로에 들어온다. 저장된 분류 ID가 로컬에 없으면 미분류로 들어가며 캐릭터 분석하지 않는다. |
| 완전 중복 | 새 자산을 만들지 않는다. 기존 자산의 분류가 요청 위치와 다르면 변경한다. 시리즈 안으로 바뀌면 예약하고, 같은 위치면 재예약하지 않는다. 미분류로 다시 가져오면 기존 분류를 해제할 수도 있다. |
| 유사 이미지 | `review` 상태에서는 캐릭터 분석을 예약하지 않는다. 검토 후 후보를 정상 자산으로 보관하는 경로에서 예약한다. |
| 미분류·등록되지 않은 상위 폴더 | 시리즈를 추측하지 않고 분석하지 않는다. |
| 등록된 시리즈와 일반 하위 폴더 | 가장 가까운 등록 시리즈 하나만 선택한다. 중첩된 하위 시리즈가 있으면 상위 시리즈 후보와 섞지 않는다. |
| 자동 분류 비활성·오리지널 역할 영역·시리즈 제외 이미지 | 예약하지 않거나 기존 작업을 무효화한다. |
| 준비된 캐릭터가 없음 | 모델 프로세스를 실행하지 않고 내부적으로 `awaiting_candidates`를 남긴다. |
| 기준 이미지가 5장뿐임 | 비교에는 참여하지만 자동 승인에 필요한 6개 일치를 만들 수 없다. 자동 분류되지 않는 것이 현재 정책이다. |
| 5개 기본 기준 + 추가 승인 기준 | 최대 25개 기준으로 비교한다. 자동 소속 이미지는 저절로 기준 이미지가 되지 않는다. |
| 한 인물을 두 캐릭터가 지지함 | 경쟁 후보 검사에서 자동 확정을 막는다. 다른 위치의 두 인물이 각각 확실하면 두 관계를 추가할 수 있다. |
| 사용자가 캐릭터를 변경·제외함 | 최신 수동 결정을 보존한다. 분석 도중 수동 결정이 바뀌어도 오래된 분석 결과로 덮어쓰지 않는다. |
| 캐릭터 화면에 외부 파일을 가져옴 | 화면 주소의 분류 ID는 소속 시리즈 ID다. 그 시리즈에 저장하고 자동 분석한다. 화면의 `characterId`를 수집 요청에 전달하거나 직접 수동 확정하지는 않는다. |
| 기존 자산을 캐릭터 폴더로 드래그함 | `move_assets_to_character`로 시리즈 범위를 검증하고 수동 관계와 분류 변경을 한 트랜잭션으로 적용한다. 외부 파일 가져오기와 다르다. |
| 기준 이미지 추가 | 이후 처리할 이미지에는 현재 기준을 사용한다. 과거 기록 갱신은 사용자가 명시적으로 요청해야 한다. |
| 과거 갱신 요청 | 요청 시점 이전의 예약 이력이 있는 미확정 자산을 32개씩 찾는다. 현재 시리즈·수동 결정·기준 변경을 재검증한다. 새 이미지 작업이 우선이다. |
| 앱 종료·재시작 | 처리 중 작업을 복구하고 이전 프로세스의 늦은 응답은 거부한다. 과거 갱신 일시 정지는 새 이미지 작업을 막지 않는다. |
| 분석 오류 | 작업별로 최대 3회 시도 후 실패 기록을 남긴다. 원래 분류와 파일은 유지한다. 다만 실패 표시 연결에 아래 문제가 있다. |

## 개선이 필요한 부분

### 1. 반복 실패와 설정 문제를 정상 대기와 구별해야 함 — 우선

`character_incremental.rs`의 작업별 오류 분기는 오류를 DB에 기록하고 다음 반복으로 넘어간다. `Status.persistent_error`는 엔진의 `error`만 읽으며 작업의 `failed` 상태나 과거 갱신의 실패 상태는 집계하지 않는다. 따라서 모델 시작 실패가 작업별 실패로 처리되면 엔진은 살아 있지만 새 분류가 진행되지 않는 상태를 UI가 놓칠 수 있다.

또한 `character_autotag_context`는 추가 기준 이미지가 무효인 캐릭터가 하나라도 있으면 시리즈 후보 전체를 비운다. 경쟁자를 몰래 제외해서 오분류하지 않는 안전장치는 필요하다. 그러나 후보가 없는 경우와 동일한 `awaiting_candidates` 처리가 되어 이유가 드러나지 않는다. 기존 테스트도 이 경우 갱신 항목이 `completed`가 되는 것을 확인한다.

제안: 조용한 기본 동작은 유지하되 지속적인 시스템 오류, 기준 이미지 문제, 단순 불일치를 구분하고 관리 화면에 원인과 복구 동작 하나를 노출한다. 오류 복구 뒤 실패 자산을 제한된 범위로 재예약한다. 파일별 검토함을 다시 만들 필요는 없다.

증거 수준: 코드 경로 확인. 실제 모델 고장에 대한 네이티브 재현은 하지 않았다.

### 2. 과거 갱신은 예약 이력이 없는 이미지까지 찾아주지 않음

시리즈 등록은 `character_series`만 저장하고 기존 자산을 예약하지 않는다. 과거 갱신 후보 SQL도 `assets` 전체가 아니라 `character_autotag_jobs`와 `character_autotag_admissions`의 내부 조인에서 시작한다.

따라서 일반 폴더에 이미지를 모은 뒤 나중에 시리즈로 등록한 경우, 기존 이미지가 예약된 적이 없다면 명시적 과거 갱신에도 포함되지 않는다. 예약됐지만 기준이 없었던 이미지와는 다른 경우다.

제안: 명시적 갱신에 한해 해당 시리즈의 미예약 정상 이미지도 상한 있는 커서로 찾고 최초 분석 경로로 연결하거나, 갱신의 현재 대상 범위를 UI에 명확히 표시한다. 자동 전체 재분석을 켜는 해결책은 피한다.

증거 수준: 시리즈 등록과 후보 SQL 연결 확인. 실제 라이브러리에 갱신을 실행하지 않았다.

### 3. 외부 가져오기와 내부 캐릭터 이동의 뜻이 다름

캐릭터 화면에서 가져온 외부 이미지는 그 캐릭터의 수동 소속이 아니다. 소속 시리즈 전체의 자동 비교 결과를 기다린다. 기준이 5개뿐이거나 결과가 애매하면 현재 캐릭터 화면에서는 새 이미지가 보이지 않는다.

제안: 캐릭터를 명시적으로 지정한 가져오기를 수동 배치로 취급할지, 시리즈 저장 후 분석이라는 안내를 보여줄지 제품 의미를 결정해야 한다. 내부 드롭과 같은 뜻으로 맞추려면 중복·유사 검토·수집 중 화면 전환까지 목적 캐릭터를 보존해야 한다.

증거 수준: `treeEntryView` → `App.dropClassificationId` → `useFileDrop` 요청과 `move_assets_to_character` 비교. 앞선 진행 메시지의 ‘미분류로 저장’ 추정은 주소 구조 확인 후 정정했다.

### 4. 오리지널 판정의 화면/서버 기준 불일치

`CharacterFolderContent.tsx`는 루트 이름이 `오리지널`인지도 검사한다. 서버는 `classification_roles`에 저장된 역할을 검사한다. 사용자 일반 폴더 이름이 우연히 같으면 화면에서 시리즈 등록이나 시리즈 화면을 잘못 숨길 수 있다.

제안: 화면도 저장된 역할 기반 정보를 사용한다. 이름이나 임의 경로를 기능 판정에 사용하지 않는다.

증거 수준: 코드 비교. 이름 변경을 실제 데이터에서 시험하지 않았다.

## 병목 후보

1. **과거 후보 탐색 범위와 불필요한 대기.** 후보 SQL은 여러 시리즈의 미확정 작업을 32개 먼저 읽고 그 뒤 시리즈를 걸러낸다. 한 페이지가 모두 다른 시리즈이면 커서는 전진해도 반환값은 0이고 실행 루프는 500ms 쉰다. 예를 들어 범위 밖 후보 10,000개만 연속해서 훑으면 대기만 약 156초가 추가될 수 있다. 이는 코드 기반 계산이지 실측값이 아니다. 시리즈 조건을 SQL에 적용하고 ‘탐색이 진행됨’과 ‘실제 유휴’를 구별하는 개선이 먼저다. 가장 가까운 등록 시리즈 규칙은 유지해야 한다.
2. **시리즈 교대 시 기준 원본 재준비.** Rust의 준비된 기준 묶음은 한 개다. A→B→A처럼 섞이면 기준 원본 열기·해시·임시 복사가 다시 발생할 수 있다. Python 특징 캐시가 있어 모델 추출은 재사용할 수 있지만 Rust 준비 비용까지 없어지는 것은 아니다. 작은 용량 제한 캐시나 짧은 동일 시리즈 묶음을 검토하되 새 이미지 우선순위를 보존해야 한다.
3. **캐릭터 수에 비례하는 비교/검증.** 한 시리즈의 모든 준비된 캐릭터가 경쟁 후보이므로 최초 처리는 후보 수와 기준 수에 영향을 받는다. 원본·기준 검증 중 DB 잠금 안에서 파일을 여는 부분도 있다. 안전 검증을 없애지 말고 기존 `LAKOMICS_CHARACTER_PROFILE`로 준비·비교·원본 확인 시간을 분리 측정한 뒤 줄일 지점을 고른다.

이미 있는 절약 장치: 이미지 특징은 한 번 불러와 후보들이 공유하고, Python 기준 특징은 용량 제한 캐시에 남는다. 과거 갱신은 유효한 기존 근거가 있으면 새로 추가된 기준만 비교하고, 바뀌지 않은 경쟁 후보 결과를 재사용한다. 실제 연동 모의 테스트에서 이 델타 경로는 통과했다.
