# PC / Galaxy Tab feature parity

Living record of features that exist on only one client (PC or Galaxy Tab), why, and whether they are being unified.
Source: a source-only audit on 2026-10-22 at `9cc31809` (no device or production checks). Update a row when its gap is closed or a decision changes; the backlog item `PARITY-20261022` tracks the implementation batches.

Policy (user, 2026-10-22): unless a feature can only work on that PC or that tablet, unify it as far as possible. PC stays canonical for design; the tablet follows in the same round with shared pieces (`AGENTS.md`, `DESIGN.md` §12). Device-bound responsibilities are listed separately in `pc-required-features.md`.

Decisions taken by the controller on 2026-10-22 (product decisions list below): follow PC-owned character recognition and the planned tablet-review retirement (no PC batch/reference/learning controls on the tablet); keep the tablet vault read-only; keep Android receive foreground-only; first implement batches A–C (existing contracts), then D–F (server/publication work) one domain at a time.

## Findings and counting

**32 Unifiable gaps, 12 Inherently device-bound capability groups, and 10 Already documented as intentional exclusions.** Counts are the individually identified U/D/I rows below, not numbers of buttons or screens. Shared features and documentation corrections are excluded. Several rows intentionally separate a PC processing responsibility from the shareable UI that consumes its results.

The largest opportunity is exposing existing data/actions consistently. Folder/Album edits, batch organization, Work creation/editing, provider connections, AV inbox/profile editing, calendars, Notes and cards already exist on both clients. Porting these entire areas again would duplicate working functionality.

Classification:

- **Unifiable (U):** no necessary device restriction. Each row states the missing side, prerequisites, rough size, and risk. S = a bounded UI/connection change; M = a feature slice with contract/native coordination; L = new publication/authority or substantial ingestion flow. These are relative sizes, not time estimates. Low/medium/high risk refers to correctness, data ownership, privacy, or media lifecycle.
- **Inherently device-bound (D):** keep the actual device responsibility. This does not forbid a remote trigger or publishing a result. It does not mean Android cannot read files or run any computation.
- **Already documented as intentional (I):** an explicit prior product/ownership decision, rather than a README capability label. Each row reassesses the reason. The present request warrants reconsidering feasible exclusions; this audit does not implement or erase those decisions.

Evidence is repository-relative `file:line`. For an absence, the citation identifies the inspected counterpart's complete menu, props, command validator, or route surface; it is not a claim that one text search proves absence. Suggested implementation is analysis, not an existing capability. Runtime availability still depends on server capability/configuration/publication.

Policy: `AGENTS.md:31`, `DESIGN.md:346`–360 require PC-first rounds, shared rules/basic parts, shared screen pieces by default, and separate data adapters. Read alongside `docs/agents/pc-required-features.md:8`, `docs/agents/mobile-consumption-ux.md:75`, `docs/roadmap/lakomics-backlog.md:155`, and the README feature list. Prior scope notes in mobile UX are historical and cannot establish current absence.

## Product decisions and retained boundaries

1. **Prior tablet exclusions:** decide individually whether I02 (merge/detach), I03 (volume ranges), I04 (reader options), I05 (Notes backup), I06 (artist metadata), I07/I08 (character management), and I09 (empty/retention) should be reopened. None becomes safe merely by adding a tablet button. Ordinary Album move U11 is independent of the protected classification move I01.
2. **Character direction:** backlog `:55` says retire tablet review, while the audit request includes character parity. Current source still has review. Recommend following PC-owned recognition and the planned retirement unless the user explicitly chooses a different direction; do not port PC batch/reference/learning controls as catch-up.
3. **Vault:** retain read-only tablet attachment unless writable-vault scope is deliberately approved; decide where vault Trash belongs and whether it requires an unlock. It is not one of the existing combined Assets/Collections/Notes tabs.
4. **Showcase ordering:** establish whether a current PC UI is intended/hidden before calling it tablet-exclusive. If explicit rearranging is wanted, build one supported order UI on PC, then tablet using the existing server order command.
5. **Media ownership:** tablet Asset file import, favourite cover-only imports, AV local artwork and saving originals are distinct operations. Use existing library/Collection authority; choose destinations and explicit user actions without converting Transfer into automatic ingestion.
6. **Statistics/activity:** choose a PC-only labeled projection versus all-device activity. Counts can be shared without agreeing to collect tablet viewing history. Local disk size and cache size remain device-specific.
7. **Local manga and video analysis results:** publishing PC-local manga requires a new media distribution/cache contract; sharing video-similarity review needs a new result feed/decision contract. Keep compute/root management on PC; treat these as separate L/high proposals, not the first parity batch.
8. **PC-off expectations:** artist/style/tag/folder-order/catalog representative changes can initially use explicit pending PC intents. If immediate PC-off application is required, server ownership work is larger. Existing server-owned Collections/AV/release/bookmark/Album actions should not acquire a new PC dependency.
9. **Android background receive:** foreground-only is the current implementation. A foreground service could extend it, but requires a notification/battery/lifetime choice rather than strict UI parity. No change is needed for direct transfer while the app is open.
