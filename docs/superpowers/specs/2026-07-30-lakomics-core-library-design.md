# Lakomics 핵심 라이브러리 설계

## 1. 목적

Lakomics는 이미지, GIF, 영상 같은 개인 미디어를 빠르게 수집하고 분류한 뒤 다시 발견하고 감상하는 Windows용 로컬 우선 라이브러리다. 게임, 만화, 영화, 애니메이션과 관련된 자산을 한곳에서 관리하며, 장기적으로는 만화 읽기, 영상 재생, 컬렉션 전시와 꾸미기로 확장한다.

첫 버전은 전시 도구가 아니라 신뢰할 수 있는 수집·분류·탐색 기반을 완성한다. 사용자는 코드를 알 필요가 없어야 하며, 브라우저에서 이미지를 끌어 도넛 메뉴에 놓는 행동이 가장 빠른 수집 경로가 된다.

## 2. 첫 버전의 범위

### 포함

- Windows 데스크톱 앱
- 하나의 통합 라이브러리
- 이미지와 GIF의 수집, 분류, 탐색, 보기
- 영상의 수집, 분류, 썸네일 및 기본 정보 관리
- 영상을 사용자가 지정한 외부 재생기로 열기
- Chromium 기반 Chrome·Edge 확장 프로그램
- 브라우저 도넛 분류 UI
- 앱으로 직접 파일 끌어놓기
- 완전 중복 차단과 유사 이미지 비교
- 계층형 분류 트리, 작품, 태그
- 기본 컬렉션 생성·이름 변경·삭제와 자산·작품 담기
- 즐겨찾기 켜기·끄기
- 최신순, 오래된순, 즐겨찾기순, 랜덤 정렬
- 기존 Lakomics 자료를 복사해 오는 일회성 가져오기
- 휴지통, 백그라운드 작업 재개, SQLite 메타데이터 백업

### 이후 별도 설계

- 앱 내부 영상 재생기
- 만화 읽기
- 컬렉션의 수동 배치, 전시 화면, 꾸미기
- 웹 영상 수집
- 오디오 감상 기능
- 모바일·macOS·Linux 앱
- 계정, 자체 서버, 자체 클라우드 동기화
- AI 검색과 고급 검색 문법
- 여러 라이브러리를 동시에 전환하는 기능

## 3. 핵심 사용 경험

### 브라우저에서 수집

1. 사용자가 웹페이지의 이미지나 GIF를 살짝 끈다.
2. 커서 주위에 두 고리 도넛이 열린다.
3. 바깥 고리에서 현재 단계의 분류 항목을 고른다.
4. 항목 위에 약 0.3초 머물면 다음 하위 단계가 같은 두 고리에 나타난다.
5. 원하는 최종 항목 위에서 놓으면 한 개의 분류 경로와 함께 수집을 요청한다.
6. 가운데에 놓으면 한 단계 뒤로 가고, 도넛 밖에 놓거나 `Esc`를 누르면 취소한다.

한 고리에는 최대 7개 항목과 `더 보기`를 표시한다. 순서는 고정 항목, 최근 사용 빈도, 가나다·알파벳순이다. `더 보기`는 같은 단계의 다음 7개를 보여준다. 끌고 있는 동안에는 별도 문자 검색을 제공하지 않는다.

브라우저에서는 한 번에 한 경로만 고른다. 한 자산을 여러 분류 항목에 넣고 싶다면 저장 후 데스크톱 앱에서 추가한다.

### 앱으로 직접 수집

사용자가 임의 위치의 파일을 앱으로 끌어놓으면 Lakomics는 파일을 라이브러리로 복사하고 사용자 원본은 그대로 둔다. 현재 선택한 분류 항목이 있으면 그곳에 넣고, 없으면 미분류함에 넣는다.

앱 전용 수집함처럼 Lakomics가 생명주기를 통제하는 위치의 파일은 수집, 무결성 확인, 메타데이터 등록이 모두 끝난 뒤에만 원본을 제거할 수 있다.

### 탐색

왼쪽 사이드바의 분류 트리가 기본 탐색 수단이다. 상위 분류를 고르면 기본적으로 모든 하위 항목의 자산을 함께 보여주며, `이 항목만` 토글을 켜면 직접 연결된 자산만 보여준다.

자산 목록은 원본 비율을 유지하면서 같은 높이의 행을 채우는 정렬 방식을 사용한다. 화면에 보이는 행과 가까운 행만 그리므로 전체 라이브러리를 매번 다시 배치하지 않는다.

정렬은 다음 네 가지다.

- 최신순
- 오래된순
- 즐겨찾기순
- 랜덤

랜덤 결과는 사용자가 `다시 섞기`를 누르기 전까지 유지된다. 검색은 보조 기능으로 제목, 원본 파일명, 작품, 태그 정도만 단순 검색한다.

### 삭제

삭제한 자산은 즉시 파일을 지우지 않고 휴지통으로 보낸다. 휴지통에서는 복원하거나 영구 삭제할 수 있다. 자동 만료는 없으며 사용자가 직접 비울 때만 영구 삭제한다.

## 4. 분류 모델

분류 트리의 모든 줄은 분류 항목이다. 분류 항목에는 다음 세 종류가 있다.

- 상위 분류: 게임, 만화, 기타처럼 사용자가 자유롭게 만드는 맨 위 항목
- 작품: 블루 아카이브, 명조처럼 여러 자산을 묶는 감상 대상
- 태그: 캐릭터, 특정 버전, 장르, 분위기 같은 특징

각 분류 항목은 부모를 최대 하나만 가진다. 하위 항목에 자산을 연결하면 모든 상위 항목에도 속한 것으로 본다. 상위 분류의 이름은 자유롭게 추가·변경·삭제할 수 있으며, 이름을 바꿔도 앱 기능은 달라지지 않는다.

작품은 별도의 태그를 중복 생성하지 않고 분류 트리에 직접 나타난다. 하나의 자산은 데스크톱 앱에서 여러 분류 항목과 연결될 수 있다.

컬렉션은 분류 트리와 다른 목록이다. 특정 주제나 전시 목적에 맞춰 자산과 작품을 골라 담는다. 첫 버전은 기본적인 담기와 빼기까지만 제공하고, 순서와 배치 방식은 컬렉션·전시 기능을 별도로 설계할 때 결정한다.

## 5. 중복 처리

### 완전 중복

수집하는 동안 파일 내용의 SHA-256 해시를 계산한다. 같은 해시의 기존 자산이 있으면 새 자산을 만들지 않고 `이미 보관된 파일`이라고 알린다.

임의 위치에서 끌어놓은 사용자 원본은 건드리지 않는다. 앱 전용 원본이라면 기존 자산 파일의 무결성을 확인한 뒤 중복 원본을 제거할 수 있다.

완전 중복 알림에서는 기존 자산을 바로 열 수 있다. 사용자가 고른 새 분류 경로를 기존 자산에 자동으로 더하는 등 기존 메타데이터를 몰래 변경하지 않는다.

### 유사 이미지

이미지의 지각 해시가 기존 자산과 충분히 비슷하면 후보를 검토 대기에 안전하게 보관하고 비교 창을 연다. 비교 창에는 두 이미지와 함께 다음 정보를 표시한다.

- 해상도
- 파일 크기
- 형식
- 출처
- 기존 작품과 태그

사용자는 다음 중 하나를 고른다.

- 기존 것 유지: 새 후보를 버린다.
- 새 이미지로 교체: 기존 자산을 휴지통으로 보내고 새 후보를 정식 자산으로 만든다. 기존 자산의 작품, 태그, 컬렉션, 즐겨찾기를 새 자산이 이어받는다.
- 둘 다 저장: 두 자산을 각각 유지한다.

새 이미지의 파일 고유 정보, 출처, 수집일은 새 후보의 값을 사용한다. 사용자가 결정하기 전까지 후보는 일반 탐색 결과에 나타나지 않는다.

## 6. 미디어 정보

모든 자산은 다음 공통 정보를 가진다.

- 안정적인 내부 식별자
- 미디어 종류
- 내용 해시
- 사용자 지정 제목
- 원본 파일명
- 라이브러리 내부 상대 경로
- 파일 크기
- 출처
- 수집일
- 현재 상태: 정상, 검토 대기, 휴지통

이미지와 GIF는 너비와 높이를 가진다. 영상은 너비, 높이, 재생 시간과 썸네일을 가진다. 이미지 자산의 즐겨찾기는 별점이 아닌 단순한 켜기·끄기 값이다.

출처는 파일 경로가 아니라 이미지를 발견한 웹페이지나 게시물의 주소다. X에서 가져올 때도 게시물 본문, 작성자 이름, 좋아요 수를 별도 저장하지 않는다. 수집일은 웹 게시일이나 파일 생성일이 아니라 Lakomics에 들어온 시각이다.

## 7. 저장 구조

사용자가 선택한 하나의 라이브러리 폴더는 다음을 포함한다.

```text
Lakomics Library/
├── library.sqlite
├── assets/
├── thumbnails/
├── trash/
└── backups/
```

- `library.sqlite`: 자산, 작품, 분류, 컬렉션, 작업 상태 같은 메타데이터
- `assets/`: 정상 자산 파일
- `thumbnails/`: 다시 만들 수 있는 미리보기 캐시
- `trash/`: 복원 가능한 삭제 자산
- `backups/`: 최근 SQLite 메타데이터 백업

자산 파일의 내부 이름은 내용 해시를 사용하고 원본 파일명은 SQLite에 보존한다. 사용자가 전체 라이브러리 폴더를 복사하면 다른 PC에서도 같은 라이브러리를 이어서 사용할 수 있다.

SQLite는 앱을 연 뒤 그날 처음으로 메타데이터를 변경하기 직전에 백업하여 최근 7일분을 순환 보관하고, 데이터 형식을 바꾸기 전에는 일일 순환과 별도의 추가 백업을 만든다. 이 백업은 목록 정보만 보호하며 미디어 파일을 복제하지 않는다. 디스크 고장까지 대비하려면 사용자가 전체 라이브러리 폴더를 외장 저장장치나 별도 동기화 도구로 백업해야 한다.

## 8. 기술 구조

데스크톱 앱은 Tauri 2, React, TypeScript로 만든다. Windows의 WebView2를 사용하고, Rust 핵심부는 데이터 손실 가능성이 있거나 많은 파일을 다루는 작업만 담당한다.

구조는 네 개의 깊은 Module로 나눈다.

### 데스크톱 UI Module

분류 트리, 자산 목록, 비교 창, 미분류함, 검토 대기, 휴지통을 보여준다. 파일을 직접 옮기거나 SQLite를 읽지 않고 라이브러리 Interface만 호출한다.

### 라이브러리 Module

수집, 조회, 분류, 중복 결정, 삭제·복원, 기존 자료 가져오기를 하나의 작은 Interface로 제공한다. 임시 파일, 해시, 트랜잭션, 썸네일, 작업 재개 같은 복잡성은 Implementation 안에 숨긴다. UI와 확장 프로그램은 이 Module의 저장 순서를 알 필요가 없다.

### 로컬 연결 Module

Chromium 확장 프로그램이 분류 트리를 조회하고 수집 요청을 보낼 수 있는 `127.0.0.1` Interface를 제공한다. 설치마다 만든 비밀 키로 요청을 인증하고 외부 네트워크에서는 접속할 수 없게 한다.

### 브라우저 확장 Module

도넛 UI와 웹페이지별 원본 주소 추출을 담당한다. X Adapter를 우선 구현하고 Pixiv Adapter와 일반 웹 Adapter를 둔다. 저장, 중복 판정, 파일 이름 결정은 확장 프로그램이 아니라 라이브러리 Module이 담당한다.

첫 버전에서 실제로 달라지는 출처가 X, Pixiv, 일반 웹 세 가지이므로 이 지점에만 Adapter Seam을 둔다. SQLite나 파일 저장처럼 대안 Implementation이 하나뿐인 부분에는 미리 Interface를 만들지 않는다.

## 9. 브라우저 연결

확장 프로그램은 앱이 실행 중일 때만 동작한다. 앱이 꺼져 있으면 저장 요청을 쌓아 두지 않고 `Lakomics를 실행해주세요`라고 즉시 안내한다. 설치별 비밀 키는 확장 프로그램의 격리된 저장소에 두고 웹페이지 스크립트에 전달하지 않는다. 로컬 연결 Module은 비밀 키가 없거나, 허용하지 않은 출처·자료 형식·크기의 요청을 거부한다.

첫 버전의 확장 프로그램은 이미지와 GIF만 수집한다.

- X: 사용자가 실제로 끈 이미지 한 장과 해당 게시물 주소
- Pixiv: 사용자가 실제로 끈 이미지 한 장과 작품 페이지 주소
- 일반 웹: 브라우저가 제공하는 이미지 주소와 현재 페이지 주소

기존 `chromias` 확장 프로그램의 도넛 사용 방식과 검증된 사이트 규칙은 참고하지만 코드는 가져오지 않는다. 기존의 거대한 스크립트, Python Native Host, Native Messaging, 웹 영상 캡처 흐름은 새 구조에 포함하지 않는다.

## 10. 안전한 수집 순서

라이브러리 Module은 모든 수집 경로에서 다음 순서를 지킨다.

1. 요청과 파일 형식을 확인한다.
2. 라이브러리 내부 임시 위치에 복사하거나 전송받는다.
3. 내용 해시와 필요한 미디어 정보를 계산한다.
4. 완전 중복과 유사 이미지 후보를 확인한다.
5. 고유한 자산이면 파일을 최종 위치로 옮기고 SQLite 변경을 한 번에 기록한다.
6. 최종 파일을 다시 확인한 뒤 성공을 알린다.
7. 앱 전용 원본만 마지막에 제거한다.

용량 부족, 권한 문제, 손상 파일, 지원하지 않는 형식이 발견되면 성공으로 표시하지 않는다. 사용자 원본은 그대로 두고 이해하기 쉬운 이유와 재시도 동작을 보여준다.

수집, 기존 자료 가져오기, 썸네일, 해시 계산은 상태가 SQLite에 기록되는 백그라운드 작업이다. 앱이 중간에 종료되면 다음 실행에서 안전한 지점부터 이어간다. 화면 탐색을 우선하고 무거운 작업은 동시에 과도하게 실행하지 않는다.

## 11. 기존 Lakomics 자료 가져오기

기존 자료 가져오기는 한 번 실행하는 복사 작업이다. 기존 앱의 데이터나 원본 파일을 이동하거나 삭제하지 않는다.

가져오는 정보는 다음과 같다.

- 원본 이미지, GIF, 영상
- 호환 가능한 작품과 태그
- 즐겨찾기
- 제목과 출처

새 Lakomics의 썸네일, 내용 해시, 지각 해시와 캐시는 새로 만든다. 완료 후 다음 결과를 보여준다.

- 발견한 파일 수
- 성공한 자산 수
- 건너뛴 완전 중복 수
- 검토 대기로 보낸 수
- 실패한 수와 이유
- 원본과 복사본의 크기·해시 검증 결과

사용자가 결과를 확인한 뒤 기존 Lakomics 삭제 여부를 직접 결정한다.

## 12. 성능 목표

목표 규모는 이미지·GIF 50,000개와 영상 5,000개다. 최초 가져오기와 미리보기 생성이 끝난 상태에서 사용자의 현재 Windows PC를 기준으로 다음을 만족해야 한다.

- 앱 실행 후 3초 안에 탐색을 시작할 수 있다.
- 분류 항목 선택 후 1초 안에 첫 자산들이 나타난다.
- 자산 수와 관계없이 화면에 보이는 행과 작은 여유분만 그린다.
- 새 자산 추가나 삭제 시 전체 라이브러리의 행 배치를 다시 계산하지 않는다.
- 썸네일 캐시는 크기 제한을 두고 오래 사용하지 않은 항목부터 다시 만들 수 있는 데이터만 제거한다.
- 백그라운드 작업 중에도 분류 이동과 스크롤이 눈에 띄게 멈추지 않는다.

정확한 시간 측정은 개발용 소량 자료가 아니라 목표 규모를 흉내 낸 성능 자료로 검증한다.

## 13. 오류 처리와 복구

- SQLite 기록과 최종 파일 이동 중 하나라도 실패하면 수집 완료로 표시하지 않는다.
- 정리되지 않은 임시 파일은 다음 실행 때 작업 기록과 대조해 재개하거나 안전하게 제거한다.
- 미디어 파일이 외부에서 사라졌다면 목록에서 조용히 숨기지 않고 `파일 없음` 상태, 원본 파일명과 예상 라이브러리 경로를 보여준다.
- SQLite를 열 수 없으면 자동으로 새 라이브러리를 만들지 않고 복구 화면을 연다.
- 백업 복원 전 현재 SQLite를 별도로 보존한다.
- 확장 프로그램의 인증 실패나 앱 미실행은 웹페이지가 아니라 확장 프로그램 알림으로 보여준다.
- 가져오기 실패는 전체 작업을 취소하지 않고 파일별 결과로 남겨 다시 시도할 수 있게 한다.

### 자동 검증

- 네 가지 정렬과 랜덤 순서 고정·다시 섞기
- 완전 중복 차단
- 유사 이미지 세 가지 결정과 메타데이터 승계
- 사용자 원본 보존과 앱 전용 원본의 성공 후 제거
- SQLite 기록 실패, 디스크 부족, 강제 종료 후 작업 재개
- 휴지통 이동, 복원, 영구 삭제
- 확장 프로그램 인증과 허용된 로컬 주소
- X, Pixiv, 일반 웹 Adapter의 출처 추출

### 통합 검증

- 브라우저에서 도넛으로 분류해 이미지 한 장 저장
- 앱에 분류된 파일과 미분류 파일 끌어놓기
- 유사 이미지 비교 창에서 각각의 선택 실행
- 외부 재생기로 영상 열기
- 기존 Lakomics 시험 자료 가져오기와 결과표 검증
- 메타데이터 백업 생성과 복원

### 성능·복구 검증

- 이미지·GIF 50,000개와 영상 5,000개 조건에서 실행·탐색 시간 측정
- 빠른 스크롤, 정렬 변경, 연속 수집 중 화면 반응 확인
- 수집과 가져오기 각 단계에서 앱을 강제로 종료한 뒤 데이터 손실과 중복 없이 재개되는지 확인

## 15. 구현 주의사항

### 하드코딩

하드코딩을 전면 금지하지는 않는다. 변하지 않는 내부 규칙을 해당 Module 안에 두는 것은 허용한다. 다음처럼 사용자 설정이나 여러 화면이 공유하는 규칙을 호출하는 곳마다 직접 적는 일을 금지한다.

- 상위 분류나 태그의 이름으로 앱 동작을 결정하지 않는다.
- 라이브러리 경로와 설치 환경에 따라 달라지는 값을 고정 경로로 넣지 않는다.
- 반복되는 간격, 색상, 글꼴 크기, 모서리, 그림자와 레이어 순서는 디자인 토큰으로 관리한다.
- 포트, 크기 제한, 시간 제한은 그 정책을 소유한 Module 한곳에서 정의한다.

같은 숫자가 우연히 두 번 등장했다는 이유만으로 공통 상수를 만들지는 않는다. 같은 의미를 가진 값이 반복될 때만 이름을 붙여 한곳에서 관리한다.

### 공통 UI

우클릭 메뉴, 팝오버, 대화상자, 알림, 버튼과 입력란은 공통 UI Module을 사용한다. 같은 기능을 새로 만들 때마다 여백, 색상, 키보드 조작, 포커스 처리와 열고 닫는 동작을 복사하지 않는다.

기존 공통 UI로 표현할 수 없는 요구가 생기면 먼저 공통 Interface에 필요한 변형을 추가한다. 실제 목적과 동작이 다른 경우에만 화면 전용 UI를 만든다. 공통 UI를 한 번 수정하면 이를 사용하는 모든 화면에 같은 결과가 적용돼야 한다.

### Module 원칙

UI는 파일 저장, SQLite, 중복 판정 같은 Implementation을 직접 알지 않는다. 각 Module은 작은 Interface 뒤에 관련 복잡성을 모은다. 반대로 미래에 필요할 것이라는 추측만으로 Adapter, 설정 계층이나 공통 도구를 만들지 않는다. 두 번째 실제 사용처에서 같은 목적이 확인될 때 공통 Module로 올린다.

이 규칙은 `docs/agents/implementation.md`에도 기록해 이후 구현 작업에서 항상 확인한다.

## 16. 첫 구현 순서

설계 승인 후 별도의 구현 계획에서 작업을 더 작은 단계로 나눈다. 큰 방향은 다음 순서를 따른다.

1. 라이브러리 폴더와 SQLite 기반
2. 안전한 이미지 수집과 완전 중복
3. 분류 트리와 자산 탐색
4. 유사 이미지 검토와 휴지통
5. 영상 관리
6. Chromium 확장 프로그램과 도넛
7. 기존 Lakomics 자료 가져오기
8. 목표 규모 성능·복구 검증

컬렉션 전시, 내부 영상 재생, 만화 읽기는 이 기반이 검증된 뒤 각각 새 설계로 진행한다.
