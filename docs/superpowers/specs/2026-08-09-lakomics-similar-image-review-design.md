# Lakomics 유사 이미지 검토 설계

## 1. 목표

이미지 수집 중 완전 중복은 현재처럼 차단하고, 파일은 다르지만 시각적으로 충분히 비슷한 이미지는 일반 자산으로 바로 확정하지 않는다. 새 후보를 미디어 금고의 검토 대기 상태로 안전하게 보관하고, 사용자가 기존 이미지와 비교해 `기존 것 유지`, `새 이미지로 교체`, `둘 다 보관` 중 하나를 결정하게 한다.

이 단계는 `docs/adr/0007-exact-and-similar-duplicates.md`와 핵심 설계의 중복 처리 규칙을 구현한다. 여러 파일을 한꺼번에 가져올 때 유사 후보 하나 때문에 전체 수집을 멈추지 않고, 나머지 수집을 끝낸 뒤 검토 대기를 한꺼번에 처리한다.

## 2. 범위

이번 단계에 포함한다.

- 64비트 지각 해시 생성과 저장
- 기존 정상 자산 중 가장 가까운 유사 후보 검색
- 검토 대기 자산과 비교 관계의 영속 저장
- 수집 결과의 저장·완전 중복·검토 대기·실패 개수 요약
- 사이드바의 검토 대기 진입점과 전체 개수
- 기존 이미지와 새 이미지의 나란히 비교
- 세 가지 검토 결정과 기존 메타데이터 승계
- 기존 자산의 지각 해시 점진적 생성
- 정상·좁은 창, 키보드, 재시작, 5만 개 해시 검색 검증

이번 단계에 포함하지 않는다.

- 휴지통에 있는 완전 중복의 복원 확인
- 누락 자산의 자동 파일 복구
- 중단된 일반 수집 작업의 영속 재개
- Chromium 확장 프로그램
- 영상 유사도
- 작품·컬렉션 기능 자체
- AI 임베딩, 색상 해시, 잘린 이미지 또는 좌우 반전 전용 감지
- 사용자가 조정하는 유사도 설정

휴지통 중복 복원, 누락 자산 복구, 일반 수집 작업 재개는 로드맵의 중단 복구·라이브러리 검사 단계에서 구현한다.

## 3. 감지 규칙

라이브러리 Module은 지원 이미지의 첫 디코딩 화면을 9×8 흑백 이미지로 축소하고, 각 행에서 이웃한 픽셀의 밝기를 비교해 64비트 difference hash를 만든다. JPEG, PNG, WebP는 본 이미지를 사용하고 GIF는 첫 프레임을 사용한다. 해시는 SQLite에 8바이트 BLOB으로 저장해 부호와 플랫폼 차이를 피한다.

새 해시와 기존 정상 이미지 해시의 Hamming distance를 계산한다. 거리가 6 이하인 후보 중 가장 작은 거리를 가진 하나를 유사 이미지로 선택한다. 거리가 같으면 기존 자산의 수집일 오름차순, 자산 ID 오름차순으로 결정해 결과를 안정적으로 유지한다. 검토 대기, 휴지통, 누락 상태 자산은 후보 검색에서 제외한다.

거리 기준 6은 라이브러리 Module의 정책이다. 첫 버전에서는 설정 화면에 노출하지 않는다. 실제 자료에서 오탐이나 누락이 반복될 때에만 보조 특징값이나 설정을 별도 설계한다.

## 4. 저장 구조

기존 `assets` 테이블에 nullable `perceptual_hash`와 nullable `perceptual_hash_error`를 추가하고 상태값에 `review`와 내부 정리용 `discarding`을 사용한다. 새 `similarity_reviews` 테이블은 다음 정보를 가진다.

- 안정적인 review ID
- 기존 정상 자산 ID
- nullable 새 검토 대기 자산 ID
- Hamming distance
- 생성 시각
- `open`, `resolving`, `resolved` 상태
- nullable 결정값과 해결 시각

새 후보 자산 하나에는 열린 검토 기록이 최대 하나만 존재한다. 해결된 행은 반복 명령을 판별하는 작은 결정 기록으로 유지하고 검토 목록에는 `open` 행만 반환한다. 일반 자산 조회는 현재처럼 `normal` 상태만 반환하므로, 사용자가 결정하기 전 후보는 전체 자산·미분류함·최근·즐겨찾기·분류 결과에 나타나지 않는다.

기존 라이브러리의 자산은 마이그레이션 직후 해시가 비어 있다. 앱은 라이브러리를 연 뒤 작은 묶음으로 해시 생성을 계속하며, 처리한 자산마다 즉시 저장한다. 앱이 종료되면 다음 실행에서 `perceptual_hash IS NULL AND perceptual_hash_error IS NULL`인 자산부터 이어가므로 별도 작업 큐를 만들지 않는다. 디코딩할 수 없는 기존 자산은 공개 오류 코드를 `perceptual_hash_error`에 기록해 무한 재시도를 막는다. 준비가 끝나기 전에도 완전 중복 검사는 정상 동작하고, 유사 검색은 해시가 준비된 기존 자산만 대상으로 한다. 상태 표시줄은 준비 중임과 실패 개수를 명확히 알린다.

## 5. 수집 흐름

라이브러리 Module은 한 파일마다 다음 순서를 수행한다.

1. 사용자 원본을 관리 임시 위치에 복사하면서 SHA-256을 계산한다.
2. 형식, 해상도와 크기를 검증한다.
3. 완전 중복이면 새 자산을 만들지 않고 기존 자산 ID를 반환한다. 기존 자산의 분류나 좋아요는 자동으로 바꾸지 않는다.
4. 지각 해시를 만들고 가장 가까운 정상 자산을 찾는다.
5. 유사 후보가 없으면 현재 수집 흐름대로 정상 자산을 등록한다.
6. 유사 후보가 있으면 관리 원본과 썸네일을 최종 위치에 설치하고, 새 자산을 `review` 상태로 등록하면서 `similarity_reviews` 행을 같은 SQLite 트랜잭션에 기록한다.
7. 결과를 `added`, `exact_duplicate`, `review_pending`, `error` 중 하나로 반환한다.

여러 파일 수집은 후보가 생겨도 FIFO 처리를 계속한다. 완료 결과는 저장, 완전 중복, 검토 대기, 실패 개수를 한 번에 보여준다. 정확한 중복과 실패 항목은 펼치면 외부 전체 경로가 아닌 파일명만 표시한다.

## 6. 검토 결정

검토 결정은 review ID와 다음 세 값 중 하나를 받는다.

- `keep_existing`
- `replace_existing`
- `keep_both`

`keep_existing`은 기존 자산을 변경하지 않는다. 첫 트랜잭션에서 review 행을 `resolving`으로 바꾸고 새 후보를 내부 `discarding` 상태로 전환한 뒤, 소유권을 확인한 관리 파일을 삭제한다. 마지막 트랜잭션은 후보 행을 제거하고 review 행의 후보 ID를 비운 뒤 `resolved`로 바꾼다. 앱이 중간에 종료되면 다음 실행에서 `resolving` review와 `discarding` 자산의 정리를 이어간다.

`replace_existing`은 기존 자산을 라이브러리 휴지통으로 보내고 새 후보를 정상 자산으로 만든다. 기존 자산의 분류와 즐겨찾기를 새 자산이 이어받는다. 새 이미지의 파일 고유 정보, 원래 파일명, 출처와 수집일은 새 후보 값을 유지한다. 작품·컬렉션 기능이 추가될 때 해당 연결도 같은 결정 트랜잭션의 승계 대상에 포함해야 한다.

`keep_both`는 기존 자산을 변경하지 않고 새 후보를 정상 자산으로 만든다. 수집할 때 선택한 분류는 새 후보가 그대로 유지한다.

각 결정은 하나의 Library Interface 호출로 실행한다. `replace_existing`과 `keep_both`의 상태와 연결 변경은 각각 하나의 SQLite 트랜잭션으로 끝낸다. 파일 정리가 필요한 `keep_existing`은 위의 재개 가능한 두 트랜잭션을 사용한다. 이미 해결됐거나 해결 중인 review ID에 같은 요청이 다시 오면 정리를 이어가거나 중복 변경 없이 해결 완료 결과를 반환한다. 다른 결정을 다시 보내면 이미 처리 중이거나 처리된 검토라는 오류를 반환한다. 외부 사용자 원본은 어떤 결정에서도 삭제하지 않는다.

## 7. Module Interface

React는 SQLite, 지각 해시, 관리 파일 경로를 알지 않는다. 라이브러리 Module은 다음의 작은 Interface를 제공한다.

```text
index_missing_similarity_hashes(limit) -> { processed, remaining }
list_similarity_reviews(after, limit) -> { items, nextCursor, totalCount }
decide_similarity_review(reviewId, decision) -> { status, nextReviewId? }
get_asset(assetId) -> AssetSummary
```

수집 결과에는 `review_pending { reviewId }`를 추가한다. 비교 목록 항목은 기존 자산과 새 후보의 공개 `AssetSummary`, 형식, 현재 분류 이름, distance만 반환한다. 내부 상대 경로와 지각 해시는 직렬화하지 않는다.

기존 해시 생성의 묶음 크기와 유사도 기준은 라이브러리 Module이 소유한다. 화면은 진행 상태와 결과만 조립한다.

## 8. 화면 구성

사이드바의 빠른 보기에 `검토 대기`를 추가하고 열린 검토 개수를 작은 배지로 표시한다. 개수가 0이어도 진입점은 유지해 위치가 흔들리지 않게 한다.

수집 작업창은 완료된 묶음을 즉시 숨기지 않고 사용자가 닫을 때까지 결과 요약을 보여준다. 검토 대기가 있으면 `유사 이미지 검토` 버튼을 표시한다. 완전 중복 목록의 각 항목은 `기존 이미지 보기`로 기존 자산을 열 수 있다.

검토 화면은 작은 대화상자가 아니라 자산 영역을 사용하는 전용 화면이다.

- 위쪽: `유사 이미지 검토`, 현재 위치와 전체 개수, 닫기
- 왼쪽: 기존 이미지와 해상도·파일 크기·형식·출처·분류
- 오른쪽: 새 이미지와 같은 정보
- 아래쪽: `기존 것 유지`, `새 이미지로 교체`, `둘 다 보관`

결정을 완료하면 다음 열린 검토로 자동 이동한다. 마지막 항목을 처리하면 빈 검토 대기 화면을 보여준다. 닫아도 해결하지 않은 후보는 그대로 남는다. 960px 좁은 창에서는 두 비교 영역을 위아래로 배치한다.

세 결정 버튼은 Tab으로 이동하고 Enter 또는 Space로 실행할 수 있다. Escape는 결정을 내리지 않고 검토 화면을 닫아 전체 자산으로 돌아간다. 실행 중에는 버튼을 비활성화하고, 실패하면 같은 항목을 유지하면서 파일 경로가 없는 오류 메시지를 표시한다.

## 9. 오류와 복구

- 디코딩, 지각 해시, 썸네일 또는 파일 설치가 실패하면 열린 검토 기록이나 반쪽 자산을 남기지 않는다.
- 검토 대기 등록은 자산 상태와 review 행을 한 트랜잭션에 기록한다.
- 검토 결정 실패 시 열린 review 행을 유지해 다시 시도할 수 있게 한다.
- `keep_existing`의 관리 파일 정리는 기존 파일 소유권 확인 규칙을 재사용하고, `discarding` 상태를 통해 재시작 후 이어간다.
- 앱 재시작 후 SQLite의 열린 review 행으로 목록을 복원한다.
- 기존 해시 생성 실패는 해당 자산 ID에 공개 오류 코드를 기록하고 나머지 자산 처리를 계속한다. 사용자가 라이브러리 검사를 실행하기 전에는 같은 실패를 자동 반복하지 않는다.
- 50,000개 지각 해시 검색은 Rust에서 수행하며 프론트엔드로 해시 목록을 보내지 않는다.

## 10. 검증

Rust 테스트는 다음을 증명한다.

- 같은 이미지의 해상도·JPEG 품질 변형은 거리 기준 안에 들어온다.
- 관계없는 시험 이미지는 거리 기준 밖에 남는다.
- 동률 후보 선택 순서가 안정적이다.
- 완전 중복은 review 자산을 만들지 않는다.
- 유사 후보는 `review` 상태와 review 행을 원자적으로 만든다.
- review 자산은 일반 목록에서 제외된다.
- 세 가지 결정이 상태, 휴지통, 분류와 즐겨찾기를 정확히 처리한다.
- 반복 결정은 중복 변경을 만들지 않는다.
- 재시작 후 열린 검토와 기존 해시 생성 진행 상태가 유지된다.
- `keep_existing` 도중 종료된 `discarding` 후보가 다음 실행에서 안전하게 정리된다.
- 50,000개 합성 해시에서 단일 후보 검색이 릴리스 빌드 기준 1초 안에 끝난다.

React 테스트는 다음을 증명한다.

- 수집 결과가 네 상태의 개수를 정확히 집계한다.
- 실패와 완전 중복 목록은 파일명만 표시한다.
- 사이드바 배지와 검토 진입점이 열린 개수에 맞게 갱신된다.
- 비교 화면이 두 자산의 공개 정보를 표시한다.
- 결정 성공 시 다음 항목으로 이동하고 실패 시 현재 항목을 유지한다.
- Escape, 키보드 포커스, 처리 중 비활성화가 동작한다.
- 960px에서 위아래 배치가 되고 가로 스크롤이 생기지 않는다.

마지막으로 `C:\Users\namwoojun\Desktop\test` 라이브러리에서 실제 Tauri 앱을 실행해 해상도와 압축률이 다른 시험 이미지, 세 가지 결정, 재시작, 외부 원본 보존을 확인한다.

## 11. 이후 단계와의 연결

이 단계가 끝나면 로드맵의 다음 작업은 Chromium 확장 프로그램이다. 그 뒤 중단 복구와 라이브러리 검사에서 휴지통 완전 중복 복원, 누락 자산 자동 복구, 영속 수집 작업을 추가한다. 영상은 별도의 미디어 해시와 비교 정책이 필요하므로 이번 이미지 유사도 Interface에 억지로 포함하지 않는다.
